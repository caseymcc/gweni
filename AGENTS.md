# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

gweni ("GUI Without Extravagant Nonsense") is a C++17 retained-mode GUI library, forked from Garry Newman's **GWEN** (MIT) and reworked to be OpenGL-aware. The core idea separating it from GWEN: instead of redrawing every widget each frame in immediate mode, controls allocate persistent renderer **primitives** and only regenerate/update them when their state actually changes. The long-term goal is good performance on modern OpenGL (3.0+ core profile) and eventually Vulkan.

The library builds as a static/object library plus example executables. Tests are run with CTest (see "Tests" under "Building"; a short version for humans is in [`docs/building.md`](docs/building.md)).

## Building

**All builds and dependency operations run inside the build container — never directly on a developer's host.** The toolchain, vcpkg, and all build tooling live in the container.

### Which situation are you in? Test `VCPKG_ROOT`

Everything below depends on whether you are *outside* the container (a developer on their own machine) or *already inside* it. Check before you run anything:

```bash
[ -n "$VCPKG_ROOT" ] && echo "inside the container" || echo "on a host — go through run_docker.sh"
```

`VCPKG_ROOT=/opt/vcpkg` is baked into the image (`Dockerfile`), so if it is set you are inside the build container and already have cmake, the compilers and vcpkg. If it is unset you are on a host; `generate.sh` detects this itself and refuses to run, pointing you at `run_docker.sh`.

### Inside the container (`VCPKG_ROOT` is set)

Run the same two steps directly — there is no docker inside the container, so `run_docker.sh` cannot work here:

```bash
./generate.sh linux                   # configure build_linux_x64_debug/
cmake --build build_linux_x64_debug -j # build
```

This is the case for an automated agent run: the agent image is built FROM this repo's own `Dockerfile`, so the container is already the environment described here. The repo is at the working directory, not at `run_docker.sh`'s `/home/developer/gweni`. Whether the vcpkg cache is available depends on how the container was started: check `VCPKG_DEFAULT_BINARY_CACHE`/`VCPKG_DOWNLOADS` — if they are unset, nothing mounted `/vcpkg-cache` and the dependency build starts cold (slow, and not reused by the next run).

### Locks on a shared host

An agent run shares its host with other agents and takes `mm run --lock ...` around what contends with them. Rendering here is Mesa's CPU rasterisers, llvmpipe (GL, the surfaceless-EGL path) and lavapipe (Vulkan), which the samples' bytes depend on, and the image pins them (`LIBGL_ALWAYS_SOFTWARE`, `VK_DRIVER_FILES` in the `Dockerfile`) even when the host passes its GPU in. So anything that opens a GL context or a Vulkan device (a headless ControlTest/OpenGLCore capture, `gweni_unittests`, a `gpu`-labelled CTest test, `tools/capture_samples.sh`) takes **`render`**, a small pool of software contexts: `mm run --lock render -- <command>`. The lock `gpu` is the host's hardware GPU, which nothing in gweni uses; the CTest label `gpu` only means "needs a context", and those tests take `render`. A timed measurement (`gweni_bench` wall times) takes `render` and `quiet` (the host otherwise idle): `mm run --lock render --lock quiet -- <command>`, one measurement per `mm run`. **Building never takes a lock** (`./generate.sh`, `cmake --build`), the headless tests take none (`ctest -LE gpu`), and neither does `tools/profile.sh` (callgrind counts instructions on one core, the same under any load). Never hold a lock around a whole `ctest`: run `-L gpu` under `render` and `-LE gpu` without one ("Tests").

### On a host machine (`VCPKG_ROOT` is unset)

`run_docker.sh` builds an Ubuntu 22.04 image (`Dockerfile`), creates a container that mounts the repo at `/home/developer/gweni`, and either attaches a shell or runs a command you pass it:

```bash
./run_docker.sh                       # interactive shell in the container
./run_docker.sh ./generate.sh linux   # run a single command in the container
./run_docker.sh cmake --build build_linux_x64_debug -j
```

Flags (before the command): `-r` rebuild the image, `-s` force-restart the container.

This path always gets a persistent vcpkg cache: `run_docker.sh` creates `.vcpkg-cache/` in the repo and mounts it at `/vcpkg-cache`, setting `VCPKG_DEFAULT_BINARY_CACHE` and `VCPKG_DOWNLOADS` into it, so the slow first dependency build is reused across container runs. `.vcpkg-cache/` and `vcpkg_installed/` are git-ignored.

### `generate.sh` is how this project is configured

**The build always goes through `generate.sh`.** It only runs `cmake` **configuration** (it does not build), and it is what points CMake at the vcpkg toolchain (`$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake`), chainloads `cmake/linux_toolchain.cmake`, pins the `x64-linux` triplet and selects the renderer options. A hand-written `cmake -B ...` configure line skips all of that and produces a differently-configured tree — it is not a valid way to build this project, even inside the container.

The commands in this section are the in-container form; from a host, prefix each with `./run_docker.sh`.

```bash
./generate.sh linux                  # configures build_linux_x64_debug/ (OpenGL core renderer)
./generate.sh linux release          # release build dir
./generate.sh linux -DSOME_OPT=ON    # any -D... arg is passed through to cmake
./generate.sh linux asan             # AddressSanitizer tree, build_linux_x64_debug_asan/ (see "ASAN tree")
./generate.sh linux profile          # profiling tree, build_linux_x64_profile/ (see "Profile tree")
./generate.sh linux gles             # GLES 3.0 tree, build_linux_x64_debug_gles/ (see "GLES tree"; release, asan too)
./generate.sh web                    # WebAssembly tree, build_web_wasm32_debug/ (see "Web tree"; web release too)
```

Dependencies are managed by **vcpkg** (manifest `vcpkg.json` at the repo root), bootstrapped into the image at `/opt/vcpkg`; `generate.sh` triggers the manifest install at configure time.

**Every tree `generate.sh` configures has Vulkan on**: it passes `-DGWENI_RENDER_VULKAN=ON` and adds the vcpkg manifest feature `vulkan` to `VCPKG_MANIFEST_FEATURES`, in debug, release, asan and profile alike, so the Vulkan tests run in every `ctest`. CMake's own default is OFF, so a plain CMake build needs no Vulkan headers or tools. `./generate.sh linux -DGWENI_RENDER_VULKAN=OFF` gives a GL-only tree (a pass-through `-D` comes after generate.sh's own and wins, and the feature is then left out); a `-DVCPKG_MANIFEST_FEATURES=...` passed to it (e.g. `boost-filesystem`) is merged with `vulkan` (`vulkan;boost-filesystem`), and the features are always passed, so one cached by an earlier configure of the tree does not linger. The image (`Dockerfile`) has the Vulkan loader (`libvulkan1`), Mesa's lavapipe CPU driver (`mesa-vulkan-drivers`, Mesa 23.2, Vulkan 1.3), Xvfb and `libwayland-dev` (which vcpkg's validation-layer port needs to build). A container from an older image lacks them (`ls /usr/share/vulkan/icd.d` tells); there `vulkan_smoke` fails with one line saying so, and from a host `./run_docker.sh -r` rebuilds the image.

Then build into the generated directory (named `build_<platform>_<arch>_<buildtype>`, `<buildtype>` being `debug`, `release` or `profile`, with `_asan` appended for an ASAN tree):

```bash
cmake --build build_linux_x64_debug -j
```

The Linux example binaries land in `build_linux_x64_debug/examples/openglcore/` (`OpenGLCore`, `ControlTest`). The build mirrors `resources/` next to them on every build (`cmake/mirrorDirectory.cmake`: a file deleted or renamed in `resources/` is removed from the tree's copy too, and an unchanged one is not rewritten) and they load it through `RelativeToExecutablePaths("resources")`, so they run from any cwd. In a window F9 toggles the depth view (`tools::DepthView`), F10 the stats overlay (`tools::StatsOverlay`), F11 the theme editor and F12 the inspector (the library binds no key; the apps' key callbacks take them before the canvas, so they work while the depth view has the input). OpenGLCore's window keeps its page in the URL (`platform::pushUrl`): a pick in the demo list pushes `?demo=<Name>`, keeping the query's other keys, and a page it shows itself (`--demo`, the stored page, back or forward, through its URL-changed handler) replaces the URL instead; the page last shown is stored (`localStorage` under `gweni-demo/` on the web, `$XDG_STATE_HOME/gweni/OpenGLCore.json` or `~/.local/state/gweni/OpenGLCore.json` elsewhere) and shown at start-up when `--demo` names none (with neither, the shell's first page is the one shown, titled and stored, the URL left bare); the title is `gweni — <Name>`; the shell's status bar has a "gweni on GitHub" link (`Demo::LinkUrl`, `platform::openUrl`). A capture does none of it, so what it draws never depends on an earlier run (`docs/architecture.md` → "The URL, history, links and storage"). `--depth-view [on|off]`, read as `--stats-overlay` is (below), opens the depth view once the first frame has numbered the z labels (`capture::openDepthViewOnce`, after each `updateCanvas()`), in a window or a capture (so does `?depth-view` on a web page). Both exes take `--stats-overlay [on|off]` (on if neither word follows; a later one overrides an earlier one) to open the overlay at start-up, in a window or a capture; a capture shows it only when asked, and a capture's phase times read a fixed profile clock (`capture::installFixedProfileClock()`, 100 µs per read), so a shot of the overlay is the same in every run. ControlTest's `--scale <s>` (or `GWENI_SCALE`; the flag wins) renders at s device px per logical unit: the canvas is `--size` logical, the framebuffer and PNGs `round(size*s)`, and scripted coordinates, the scenarios' sizes and `--dump-bounds` stay logical. `OpenGLCore --scale <s>` (or `GWENI_SCALE`) keeps its 1024x768 framebuffer and makes the canvas `round(1024x768/s)` logical, so the UI is drawn s times as large. In a window both multiply the OS content scale (`glfwGetWindowContentScale`, followed by its callback; an offscreen capture and EGL count as 1), through `capture::fitCanvasToWindow`, which also keeps `input::GLFW3`'s cursor mapping (`windowToLogical`) current (`docs/architecture.md` → "Where the scale comes from"). `--resources <dir>` (relative to the cwd, or absolute) loads the skin, fonts and textures from `<dir>` instead, e.g. `--resources resources` from the repo root to pick up live `DefaultSkin.json` edits without a rebuild. A missing resource dir, skin config, default font or a face the config names for the mono role or the glyph fallback chain prints one line naming the path tried and the run carries on degraded (every surface magenta for a missing skin config, the text in the built-in OpenSans for a missing font, the default face for a missing mono one; `docs/architecture.md` → "Missing resources"): a window keeps running, and a capture (any ControlTest mode but the window, `OpenGLCore --screenshot`/`--frames`) writes what it drew and exits **2**, after `<exe>: resources incomplete, exiting 2`, unless something else failed (exit 1 wins). `gweni_bench` still exits 1 on any of them. `controltest_missing_resources*` and `openglcore_missing_resources*` (`tests/missingResources.cmake`) run a capture from a copy of `resources/` missing the directory, `DefaultSkin.json`, `OpenSans.ttf` or `DejaVuSansMono.ttf` (exit 2, the PNG written, the path on stderr) and a complete copy (exit 0, nothing on stderr; ControlTest captures the demo shell, `--control Demo`, so every page is built). A capture runs on a stepped clock (1/60 s per frame, whole steps read as `steps*(1.0/60)` in double, as the library's clock `platform::getTimeInSeconds()` is a double of seconds since start, so a window open for a month still resolves a frame, `tests/unit/longClock.cpp`); `--stats` freezes it, so an idle frame is genuinely idle, and `--stats-clock step` keeps it stepping, for the counters of something that waits on time (a tooltip's delay, an animation). Both exes take `--headless` with a capture (`OpenGLCore --screenshot`/`--frames`, ControlTest's `--shot`, `--shot-all`, ...): it goes straight to the surfaceless-EGL context instead of trying a GLFW window first, so a capture renders the same whether or not a display exists. Without a capture it is an error, and so it is in a build without the EGL path (`GWENI_EXAMPLE_EGL` off). Both exes and `gweni_bench` take `--renderer gl|vulkan` (default `gl`, or `GWENI_RENDERER`; the flag wins): `vulkan` draws with `renderer::Vulkan` on a headless Vulkan device and `VulkanTarget`, creating no GL or EGL context. What a run draws with is a `capture::Device` (`capture::openDevice`, `examples/openglcore/capture.h`: the GL context, a window, a hidden one or surfaceless EGL, with the offscreen `Framebuffer`, or the Vulkan device and target), which makes its renderer (`newRenderer`), resizes the target and waits for it (`finish`); a frame clears through `SlotRenderer::clearTarget` and a capture reads back through `SlotRenderer::readPixels` (`capture::writeRendererPng`), on GL the `glClear`/`glReadPixels` they always were. On Vulkan every capture mode, with or without `--headless`, is the same headless run (`--renderer vulkan` in a tree built without Vulkan prints one line and exits 1). Without a capture it is the window: a GLFW window with no client API (`GLFW_NO_API`), its Vulkan surface and a FIFO swapchain (`examples/openglcore/vulkanWindow.cpp`, a `capture::Device` like the others), the same loop as GL's through `Device::runWindowLoop` (`beginWindowFrame`, the frame, `presentWindowFrame`, a frame not shown marking the canvas for another): renderer::Vulkan draws into the device's `VulkanTarget` at the framebuffer's size, and each frame blits it, turned top-down, into an acquired swapchain image and presents it, two frames in flight; a new framebuffer size (the size callback has fitted the canvas and view through `fitCanvasToWindow`) and an out-of-date or suboptimal acquire or present make the target and the swapchain again, and while the window is iconified or its framebuffer 0x0 nothing is drawn, acquired or presented and the loop waits in `glfwWaitEvents` (`docs/architecture.md` → "The Vulkan window"). ControlTest's `--window-test <dir>` scripts that window (no input callbacks, the stepped clock, one frame drawn per step whatever `--loop` says): it presents at `--size`, resizes itself to 5/4 and 4/5 of it and back, iconifies and restores, writes each presented image it read back (`window_<i>_<W>x<H>.png`, `window_restored_<W>x<H>.png`) and prints its swapchain's counts; it needs `--renderer vulkan`, a window manager to iconify with and `--scale` 1. The interactive window's clipboard is the system's (`input::GLFW3::useSystemClipboard`, installed for a shown GL window and the Vulkan window by `capture::DeviceOptions::systemClipboard`, which `--window-test` turns off; in a browser page the browser's), and every capture's an in-process buffer, so what a capture pastes never depends on the host (`docs/architecture.md` → "The clipboard"). ControlTest's `--clipboard-test` runs a script (`--key`, `--type`, ...) in a shown GL window with the system clipboard instead of offscreen, and its `--wait-clipboard-change <s>` step polls the window's events (which serve the X selection) until another client has changed the clipboard, failing after `<s>` seconds. `GWENI_VULKAN_VALIDATION=1` enables `VK_LAYER_KHRONOS_validation` with a messenger that aborts on any warning or error, and fails the run without the layer; the Vulkan tests set it.

### Running the examples

`./run.sh [-b] [debug|release] [asan] [opengl|controltest] [args...]` runs one of them from any cwd (defaults `debug`, `opengl`; `asan` is `build_linux_x64_debug_asan/`). The first argument that is none of its words, and everything after it, goes to the exe unchanged, and the exe runs in the caller's cwd, so relative `--shot`/`--screenshot`/`--resources` paths mean what was typed. It never injects `--resources`. `-b` builds first (`cmake --build`, through `./run_docker.sh` when `VCPKG_ROOT` is unset) and stops with the build's exit status if it fails; without `-b` it never builds. A missing build tree or exe prints the path and the `generate.sh`/`cmake --build` commands, and exits 1. `./run.sh -h` is its usage; `./run.sh controltest --help` is ControlTest's. Nothing may depend on `run.sh`: scripts and tests call the exes directly.

- On a host: `./run.sh`, `./run.sh -b`, `./run.sh controltest --control ButtonDemo`, and on Vulkan `./run.sh opengl --renderer vulkan`, `./run.sh controltest --renderer vulkan --control ButtonDemo` (the host needs a Vulkan 1.3 driver and the loader, `libvulkan.so.1`; `docs/building.md` → "Vulkan in a window"). The container-built exes need the host's glibc ≥ 2.34, GCC 11+ libstdc++ (`GLIBCXX_3.4.29`) and a glvnd GL driver (`libGLX.so.0`, `libOpenGL.so.0`, `libEGL.so.1`), e.g. Ubuntu 22.04+, Debian 12+, Fedora 35+; the vcpkg deps are static. The image is built with the host UID/GID, so the build output is owned by the developer.
- In the container (an agent run) there is no display, so only the headless modes work: `./run.sh controltest --headless --shot /tmp/x.png` or `./run.sh --headless --screenshot /tmp/x.png`, under the `render` lock (`mm run --lock render -- ./run.sh ...`); `./run.sh controltest --renderer vulkan --shot /tmp/x.png` is the same on Vulkan. Plain `./run.sh` execs `OpenGLCore`, which fails to open a window; that is expected.

### Regenerating the UI samples

The sample PNGs under `docs/images/` (embedded by `README.md`) are checked in and regenerated by one script, run inside the container after a normal build (from any cwd):

```bash
./tools/capture_samples.sh                 # rewrite docs/images/
./tools/capture_samples.sh --check         # compare with docs/images/, write nothing there
./tools/capture_samples.sh --bin-dir DIR   # take OpenGLCore/ControlTest from DIR
```

It captures the hero demo (`OpenGLCore --headless --demo`) and the gallery controls (`ControlTest --headless --control`) with `--headless`, always through the surfaceless-EGL path, so no display is needed and having one changes nothing. It loads the repo's `resources/` (`--resources`), not the copy next to the exes. `--bin-dir` defaults to `build_linux_x64_debug/examples/openglcore`. `--check` captures the same set through the same `capture()` into a `mktemp -d` dir and compares each PNG byte for byte with `docs/images/`, printing `differs: X.png`, `missing from docs/images: X.png` or `not in the sample set: X.png` (any other PNG there). It exits 1 on any of them and keeps the scratch dir, printing its path so the new captures can be looked at. If everything matches it exits 0 and removes the dir. The `SAMPLES` list at the top of the script is the interface: edit it to change the set, and update the gallery in `README.md` to match, since it embeds each PNG by path in that order, one per row, each image a link to its live page (`[![...](docs/images/<Name>.png)](https://caseymcc.github.io/gweni/controltest.html?control=<Name>)`; `tools/check_site_links.py` checks the set, the order and the links; `docs/building.md` → "Publishing the site"). Each sample is captured at its entry in the `SAMPLE_SIZE` map, or by default at `PANE_SIZE`, the shell's centre pane (865x545), so a showcase page (`examples/demo/showcase.h`) looks in the gallery as it does in the hero. Re-running on an unchanged tree produces byte-identical PNGs.

CTest runs `--check` as `docs_samples`, in the `gpu` set (see "Tests"). So **a commit that changes how a sample looks must regenerate the samples in that same commit**: run the script, look at every PNG that changed, and commit them with the change. The bytes match only inside the pinned build container (its Mesa llvmpipe and compiler), so a `docs_samples` or `--check` failure on a host means nothing. The debug, ASAN and release trees render the same bytes, so `docs_samples` is registered in every tree. A difference between them is a bug, not -O2 pixel noise: the release-only 20 px wider PropertyTree of issue #248 was undefined behaviour (the CheckBox and ComboBox renderers `static_cast`ing the `property::` controls that share their names).

### Tests

The test suite is CTest, under `tests/`. After `cmake --build`, from the repo root:

```bash
mm run --lock render -- ctest --test-dir build_linux_x64_debug -L gpu   # the tests that need a GL context or Vulkan device
ctest --test-dir build_linux_x64_debug -LE gpu                          # the rest (the headless unit tests), no lock
mm run --lock render -- ctest --test-dir build_linux_x64_debug -L gpu -LE vulkan  # the GL-only suite's context tests
ctest --test-dir build_linux_x64_debug                                  # everything, on a machine of your own (no mm)
```

On a shared host the suite is those two runs, `-L gpu` under the `render` lock and `-LE gpu` with none, never one lock around a whole `ctest` ("Locks on a shared host").

Every Vulkan test carries the label `vulkan` as well as `gpu`, so `ctest -LE vulkan` runs the suite as it is without them. A Vulkan test is registered only when `GWENI_RENDER_VULKAN` is on, and gets its environment and both labels from `gweni_vulkan_test_environment(<test>...)` (`cmake/Vulkan.cmake`): `VK_LAYER_PATH` holding only the vcpkg `VK_LAYER_KHRONOS_validation` (a copy of its manifest in `<tree>/vulkan/explicit_layer.d/` naming the library by its absolute path, since the installed one names it bare), and `VK_ICD_FILENAMES`/`VK_DRIVER_FILES` pinned to lavapipe (`GWENI_VULKAN_TEST_ICD`, found at configure time). The pin matters beyond determinism: on a host whose GPU the container's Mesa does not know (radv on a Radeon 8060S), the loader fails `vkEnumeratePhysicalDevices` for every device, lavapipe included. A Vulkan test enables the layer and a debug-utils messenger that prints any validation warning or error and aborts, and fails if the layer is not there. Every whole-app check (a `controltest_*` or `openglcore_missing_resources*` test, and `bench_smoke`) is registered once per backend: on GL, and with `GWENI_RENDER_VULKAN` as `<name>_vulkan`, by `gweni_whole_app_test(<name> <timeout> COMMAND ...)` in `tests/CMakeLists.txt` (`bench/CMakeLists.txt` registers `bench_smoke_vulkan` the same way): the same command, the backend chosen by `GWENI_RENDERER` (`gl` for the first, `vulkan` for the second), which the exes take as their `--renderer` default, so a script's own ControlTest and OpenGLCore children take it too and no script has an argument for it; `@VARIANT@` in its arguments is `""` or `_vulkan`, so each variant has its own scratch and `--shot-dir` directories, and the Vulkan one twice the timeout. Left GL only: `docs_samples` (the samples are GL-rendered), `controltest_verify_layout_*`, `controltest_verify_idle_*`, `controltest_demo_labels*` and `controltest_any_cwd` (layout, what the canvas reports as work and paths, which the backend does not touch), `bench_scaling`.
`backend_counters`, `backend_pixels` and `backend_pixels_scale200` (`tests/backends.mjs`, on emsdk's node, `GWENI_NODE`; its header says what each mode runs) hold Vulkan to GL in the same tree: every counter of every `gweni_bench` scene (N=50, 3 frames), every `ControlTest --stats` control and `OpenGLCore --stats` identical on both backends (the times, the bench's `allocs*`/`alloc_bytes*`, which count the backend's own allocations, and `renderer=`/`device=` left out, each with its reason in the script), every settled Vulkan frame writing and uploading nothing; and every `--shot-all` PNG, the hero and the depth view's shots (`--scenario depth-view`), at scale 1 and 2, within the bound `tests/CMakeLists.txt` sets beside its measurement (max |Δ| 1, at most 0.01 % of the pixels differing at all; the feature's ceiling is 2 and 0.5 %, and a PNG over it is a bug to find, never a reason to widen it), a failure keeping its `/tmp/gweni-backends-*` dir with `diff/<name>.diff.png`. The shared fragment bodies use `lerp()`, never `mix()`, which Mesa's GLSL compiler and lavapipe lower to different arithmetic, and style 4's vertical gradient is an exact integer level per row, `(top*2H + (bottom-top)*(2r+1) + H) / (2H)` (round half up; `tests/gradientRows.cpp`), since a float one lands on an 8-bit tie on some rows, where an ulp of the interpolated position decides the level (`docs/architecture.md` → "Vulkan's counters and pixels against GL's").
`vulkan_smoke` (`tests/vulkan/vulkanSmoke.cpp`, out of the `tests/*.cpp` glob) is the plumbing's check; its header comment says what it pins.
`window_idle` (label `gpu`) and `window_idle_vulkan` (`gpu`, `vulkan`, validated) (`tests/windowIdle.cmake`, its header says what it runs) start their own X server (`xvfb-run -a`) and run `ControlTest --idle-test` on ButtonDemo: once the canvas has settled the window idles 2 s, which must draw no frame, swap or present nothing and take under 0.1 s of the process's CPU (`getrusage`, every thread), then a post from another thread must wake the loop and draw exactly one frame (writing glyph slots, one swap or present), and a canvas timer closes the window; `window_idle_demo` (`gpu`, GL) runs the same on the whole demo shell (`--control Demo`), so a hidden page's animation that keeps the loop drawing fails it (an animation that waits while hidden returns `+inf` from `nextThinkTime()`, as the ProgressBar's and LogViewDemo's stream do); without `xvfb-run`/`Xvfb` they fail, saying so.
`window_vulkan` (`tests/windowVulkan.cmake`, labels `gpu` and `vulkan`, the Vulkan window's sign-off; its header says what it runs) starts its own X server (`xvfb-run -a`, a 1280x1024x24 screen) and `gweni_test_wm` in it (`tests/vulkan/testWindowManager.cpp`, the least window manager that makes an iconify real: Xvfb has none), runs `ControlTest --renderer vulkan --window-test` on ButtonDemo at 640x480 and captures each size it presented at `--headless`, and fails unless all five presented images are byte-identical to those captures, every resize recreated the swapchain, nothing was drawn or presented while the window was iconified (the loop waiting instead) and nothing was reported by the validation layer; a hang is its 300 s timeout. Without `xvfb-run`/`Xvfb` on `PATH` (or without the X11 headers `gweni_test_wm` is built with) it fails, saying so; it never skips.

C++ unit tests use **doctest** and build into two executables: `gweni_unittests` for the ones that need a GL context, and `gweni_unit_tests` for the headless ones (below).
`gweni_unittests` is registered as the CTest test `unittests`, label `gpu`, and built from every `tests/*.cpp`.
Its `main.cpp` creates a surfaceless EGL context through the examples' `gweni_capture` library (`examples/openglcore/capture.{h,cpp}`), plus one init()'d `OpenGLCore` with OpenSans loaded, and then runs every case.
With `GWENI_RENDERER=vulkan` it creates a validated Vulkan device (`renderer::createVulkanDevice`), a `VulkanTarget` and a `renderer::Vulkan` instead, with no GL or EGL context (`docs/architecture.md` → "renderer::Vulkan (headless)"); in a tree without Vulkan that prints one line and exits 1.
`unittests_vulkan` (labels `gpu` and `vulkan`, registered with `GWENI_RENDER_VULKAN`) is that run: every case but the `gl_only` suite, text in every mode included.
Run it by hand as `GWENI_RENDERER=vulkan VK_LAYER_PATH=$PWD/build_linux_x64_debug/vulkan/explicit_layer.d build_linux_x64_debug/tests/gweni_unittests ...` under the `render` lock (the layer path is what `gweni_vulkan_test_environment` sets).
A test reaches them through `test::gpuRenderer()` / `test::openSans()` (`tests/gpuRenderer.h`), the renderer as the backend-independent `renderer::SlotRenderer`, and clears and reads the target through `test::clearView()` / `test::readView()` (a renderer of its own: `test::newRenderer()`), so a test is written once for every backend and only `main.cpp` names `OpenGLCore`.
A test of something only GL has (`fontRelease.cpp`'s GL objects, `glslDialects.cpp`, `textDrawLoop.cpp`'s and `primitiveDrawLoop.cpp`'s multi-draw) is in the doctest test suite `gl_only` (`TEST_SUITE_BEGIN("gl_only")`, or `* doctest::test_suite("gl_only")` on one case; `test::glRenderer()` in `tests/glRenderer.h`) and says why in its header comment; a run on another backend leaves the suite out (`-tse=gl_only`).
Do not define a second `main`.
The executable is only built when `gweni_capture` exists (`GWENI_BUILD_EXAMPLES`).
It must run from the repo root, because it loads `resources/`.
Run one case with `build_linux_x64_debug/tests/gweni_unittests -tc="<name>"`, holding the `render` lock as for any other capture (`mm run --lock render -- build_linux_x64_debug/tests/gweni_unittests -tc="<name>"`).

Headless unit tests, which need no GL context, live in `tests/unit/` and build into `gweni_unit_tests`, from every `tests/unit/*.cpp` (`unit/main.cpp` holds its doctest `main`).
`doctest_discover_tests` registers each case as its own CTest test, `unit:<case name>`, with no `gpu` label, so `ctest -LE gpu` runs them without a lock.
`tests/unit/headlessFixture.h` is the fixture for skin/control/id-bank tests: a `StubRenderer` that draws nothing and forwards primitive/text id requests to the real process-global banks (recording each one, and each `drawLine` call in `lines` with the draw colour it was made in) and counts what each frame's draws wrote, every draw a write, for `renderer::Base::frameStats()`/`writtenPrimitiveIds()`/`writtenTextIds()` as `SlotRenderer` reports them (`tests/unit/frameCounts.cpp`), a `StubSkin` handing out a `StubControl` for any type name, and a `StubText` control whose Control also takes a text id.
The bank state is read through the `primitiveIdCount()`/`releasedPrimitiveIds()`/`textIdCount()`/... accessors in `primitiveIds.h`.
The banks are shared by every case in the process, so assert deltas from a baseline taken at the start of the case, never absolute counts.

**Adding a test is adding one file.** A new test is a new `.cpp` in `tests/unit/` (headless) or `tests/` (needs a GL context), with `#include <doctest/doctest.h>` (or `headlessFixture.h` / `gpuRenderer.h`) and `TEST_CASE`s.
The `file(GLOB CONFIGURE_DEPENDS ...)` in `tests/CMakeLists.txt` picks it up: the next `cmake --build` re-runs the configure step itself (or re-run `./generate.sh`). Neither `tests/CMakeLists.txt` nor this file needs an edit.
Each test file opens, after its license header, with a comment saying what it pins; that comment is where a test is described, not here.
Read it before you change what a test covers, and keep it true when you do.

### ASAN tree

`./generate.sh linux asan` configures a second tree, `build_linux_x64_debug_asan/` (`asan` combines with `release` too: `build_linux_x64_release_asan/`), with `-DGWENI_SANITIZE=address`. It builds and tests like the plain one:

```bash
./generate.sh linux asan
cmake --build build_linux_x64_debug_asan -j
mm run --lock render -- ctest --test-dir build_linux_x64_debug_asan -L gpu --output-on-failure
ctest --test-dir build_linux_x64_debug_asan -LE gpu --output-on-failure
```

The sanitizer flags are set before `deps/` is added, so gweni, the examples, the tests and the vendored freetype-gl and imglib are instrumented. The vcpkg-installed dependencies are not. In that tree every test runs with `ASAN_OPTIONS=detect_leaks=0:abort_on_error=1` (`tests/CMakeLists.txt`): Mesa/EGL leak at exit and that is not ours, so leak checking is off and only memory errors fail a test. An ASAN report aborts the process, and that fails the test, including a ControlTest child of `determinism.cmake`. Run one binary by hand with the same `ASAN_OPTIONS`.

The heap-string case in `tests/textLength.cpp` is a real check only in this tree. If `OpenGLCore` passes freetype-gl a byte count again (the `cca344a` bug), ASAN reports `heap-buffer-overflow` in `deps/freetype-gl/text-buffer.c`. ControlTest's UnicodeTextDemo also triggers that report.

**ASAN does not catch an over-read that stays inside one object.** ListBoxDemo's original instance of this bug read past a short string held in SSO storage inside `controls::Text`, into the neighbouring `m_font` field. That memory is addressable, so ASAN and valgrind both stay silent. The deterministic trailing-bytes test in `textLength.cpp` exists for that case, and so does the two-process determinism test.

### GLES tree

`./generate.sh linux gles` configures `build_linux_x64_debug_gles/` (`gles release`: `build_linux_x64_release_gles/`; `gles asan`: `build_linux_x64_debug_gles_asan/`; `gles profile` prints one error and exits 1), with `-DGWENI_GL_ES=ON`: `OpenGLCore`, the examples, the tests and the bench compile against `<GLES3/gl3.h>` (and `<GLES2/gl2ext.h>`) and link `libGLESv2` and `libEGL`, with no glew anywhere in the tree, so a GL call newer than GLES 3.0 does not compile. It builds and tests like the desktop tree, Vulkan included:

```bash
./generate.sh linux gles
cmake --build build_linux_x64_debug_gles -j
mm run --lock render -- ctest --test-dir build_linux_x64_debug_gles -L gpu
ctest --test-dir build_linux_x64_debug_gles -LE gpu
```

The choice of headers is made in one place, `include/gweni/platforms/renderers/glApi.h` (glew on desktop, the GLES headers with `GWENI_GL_ES`, a public compile definition of `gweni`, or under Emscripten); every file that calls GL includes it, `GLFW_INCLUDE_NONE` keeps `<GLFW/glfw3.h>` from including the desktop `<GL/gl.h>`, and the vendored freetype-gl takes the same switch from `freetype-gl_WITH_GLES3` (a gweni patch: `FREETYPE_GL_GLES3` in its `opengl.h`). The context is GLES 3.0: the surfaceless EGL path (`capture::initEglContext`) binds `EGL_OPENGL_ES_API` with an `EGL_OPENGL_ES3_BIT` config, and a window asks GLFW for `GLFW_OPENGL_ES_API` 3.0 (only compiled in the container, which has no display). `capture::initGL` (glewInit on desktop, nothing to load on GLES) and `createFramebuffer` check, in every tree, that the window's or the offscreen framebuffer's depth buffer has at least 24 bits, and fail with one line if not. Every test passes there as in the desktop trees, `docs_samples` byte for byte included, and `gweni_bench`'s counters are the desktop tree's: llvmpipe's GLES context has `GL_EXT_multi_draw_arrays` (its `glMultiDrawElementsEXT` comes from `eglGetProcAddress`) and `GL_EXT_blend_func_extended`, so it draws through the same calls. In that tree `tests/glslDialects.cpp` compiles the ES shader bodies natively and skips the desktop ones. It is the native reference for the web tree's comparisons.

**Without dual-source blending** (a GLES context without `GL_EXT_blend_func_extended`, WebGL 2) the LCD text modes fall back to grayscale: `SlotRenderer::lcdTextUnavailable()` says why (`lcdTextAvailable()` is false), `setTextAA(LcdRGB/LcdBGR)` and `GWENI_TEXT_AA=rgb|bgr` leave `textAA()` at `Grayscale`, and the renderer logs one warning the first time an LCD mode is asked for. `GWENI_GL_NO_DUAL_SOURCE=1` at construction makes `OpenGLCore` take any context to have none, and a `renderer::Vulkan` on a `VulkanDevice` whose `dualSourceBlend` is off draws with its single-output text shader, so `tests/noDualSource.cpp` checks the fallback on both backends in every tree (`test::newRendererWithoutDualSource`).

### Web tree

`./generate.sh web` configures `build_web_wasm32_debug/` (`./generate.sh web release`: `build_web_wasm32_release/`), a WebAssembly build: `CMAKE_TOOLCHAIN_FILE` is vcpkg's as everywhere, the triplet `wasm32-emscripten` (vcpkg's community triplet, which builds the ports with Emscripten found through `EMSDK`), and `VCPKG_CHAINLOAD_TOOLCHAIN_FILE` emsdk's own `upstream/emscripten/cmake/Modules/Platform/Emscripten.cmake`. `generate.sh` sets `CMAKE_CROSSCOMPILING_EMULATOR` to emsdk's node (`EMSDK_NODE`, or `$EMSDK/node/*/bin/node`), since `Emscripten.cmake` would take whichever node is first on `PATH`. `asan` and `profile` do not combine with `web` (one error line, exit 1), and neither does Vulkan (off, with no vcpkg feature). Without emsdk (`EMSDK` unset, or no `Emscripten.cmake` under it) it prints one line naming what is missing and exits 1, as it does without `VCPKG_ROOT`.

The tree has `OpenGLCore` (on WebGL 2) and the examples on, and Vulkan and `gweni_bench` off. It builds the `gweni` library, the textured skin, `gweni_unit_tests` (`gweni_unit_tests.js` + `.wasm`) and three **pages**: `examples/openglcore/ControlTest.html`, `OpenGLCore.html` and `tests/gweni_unittests.html`, each with its `.js`, `.wasm` and `.data`. `gweni_web_page(<target>)` (`examples/openglcore/web/page.cmake`, also called for `gweni_unittests`) makes a target a page:
- `shell.html`, with the `#canvas` the context is made on and an `#output` panel;
- `pre.js`, which turns the URL query into argv (`key=value` is `--key value`, a bare `key` is `--key`, `argv=<text>` one argument verbatim; under node, which has no URL, it keeps node's argv, so `node ControlTest.js --list` works; a page that keeps its own state in the query sets `Module.gweniQueryArgs = false`, and main gets `Module.gweniDefaultArgs` alone, the app reading `platform::currentUrl()` itself; it never reads the path) and records the run in `window.gweniRun`: the arguments it gave main (`argv`), the exit code, an abort, every stdout/stderr line in order, the WebGL context, and the files under `/out`; a page may set `Module.gweniDefaultArgs` (a global `Module` defined before the Emscripten script), which come before the URL's, so the URL's can override them (`tools/site/demo.html` sets `['--stats-overlay']`, and `?stats-overlay=off` turns it off again);
- `resources/` preloaded at `/resources` (the fonts' `*-LICENSE.txt` left out: nothing loads them, and the site ships them as files), relinked when a file under it changes;
- a heap that grows, a 4 MB stack (Emscripten's default is 64 KB) and `-sEXIT_RUNTIME`.

The release web tree is `-Oz` (`CMAKE_<LANG>_FLAGS_RELEASE`, top-level `CMakeLists.txt`), not `-O3`: it is the hosted site, and `-Oz` makes `ControlTest.wasm` 975 kB gzip against 1080 kB, with no measurable slowdown. Everything in the tree is built with `-fexceptions` (top-level `CMakeLists.txt`, before `deps/`), so a C++ throw is caught as natively instead of aborting the page. That is Emscripten's JavaScript exception handling: `-fwasm-exceptions` does not link with the vcpkg ports' JavaScript setjmp/longjmp (libpng, FreeType). GL is Emscripten's `<GLES3/gl3.h>` (`glApi.h` defines `GWENI_GL_ES` under `__EMSCRIPTEN__`, and freetype-gl takes `freetype-gl_WITH_GLES3`), linked at WebGL 2 through `gweni`'s INTERFACE link options. GLFW is the `contrib.glfw3` port behind an INTERFACE target named `glfw` (`examples/openglcore/CMakeLists.txt`). A page runs either mode, as the native exe does. A capture (`--headless` with `--shot`, `--shot-all`, `--screenshot`, `--stats`, ...) is one blocking `main` that renders into the offscreen framebuffer and reads it back, so it needs no main loop. Without one, the page is the interactive window: `capture::initGlfwContext` makes emscripten-glfw's window on `#canvas` with a WebGL 2 context (`GLFW_CONTEXT_VERSION_MAJOR` 2 is the WebGL version there; depth 24, no alpha, stencil or antialiasing) and `GLFW_SCALE_FRAMEBUFFER`, so the framebuffer is the canvas's CSS size times `devicePixelRatio` and the content scale `devicePixelRatio`. It keeps the canvas at the size of the shell's `#canvas-container` (`emscripten_glfw_make_canvas_resizable`), which is the page less the fixed 96 CSS px `#output` panel under it (`examples/openglcore/web/shell.html`). A page resize and a `devicePixelRatio` change reach the app as GLFW's framebuffer-size and content-scale callbacks, through the same `capture::fitCanvasToWindow` as on a desktop, and `--scale` multiplies them; `--size` is only the window's first size. `capture::runWindowLoop` is the one loop both apps' windows run, on `input::GlfwLoop` (`include/gweni/platforms/input/glfwLoop.h`, over the window-system-free `platform::IdleLoop` of `gweni/platforms/idleLoop.h`): natively, idle (the default, `--loop idle`), a `frame()` and swap only when the canvas has work (`Canvas::nextWorkTime()`), blocking in `glfwWaitEventsTimeout`/`glfwWaitEvents` in between (the canvas's wake handler is `glfwPostEmptyEvent`, a window refresh marks the canvas), or with `--loop continuous` `frame()`, swap and poll every iteration, until the window closes; in the browser `emscripten_set_main_loop_arg` at the browser's rate, each callback a `glfwPollEvents()` (where emscripten-glfw applies a resize; it delivers input as it comes) and `frame()`, with no `glfwSwapBuffers` (emscripten-glfw only logs that it is not implemented), idle there too: a callback with nothing to do (`Canvas::nextWorkTime()` past now and no frame wanted: the canvas's wake handler sets that flag) returns at once, and the main loop is never paused (a missed wake would freeze the page). It never returns there, and main's stack is unwound before the first frame, so the frame (`updateCanvas`, `glClear`, `renderCanvas`, in both apps and both builds) captures only the heap canvas. Each callback sets `gweniRun.frames` (frames drawn) and `gweniRun.ticks` (callbacks), so an idle page's ticks go on while its frames stand still; the page scripts wait for a page to settle (`tests/web/frames.mjs`: drawn since the call, or a tick passed with no frame), never for some more frames. ControlTest exports `gweni_web_post()` too, a `Canvas::post` of a `redraw()`, which an idle page draws once. Input goes through the GLFW callbacks and `input::GLFW3` as natively: mouse moves, both buttons, the wheel, keys with modifiers and typed characters (a non-ASCII one included). emscripten-glfw also sends Ctrl+letter's letter as a char event after its key event, which ran the accelerator twice (a paste pasted twice); `GLFW3::processCharEvent` drops a char that follows a Ctrl+letter press. To use a page by hand, serve its directory over HTTP (a page cannot load its `.wasm` and `.data` from `file://`) and open it with the program's arguments as the URL query (`pre.js`: `key=value` is `--key value`, a bare `key` is `--key`, in order, URL-decoded): on a host, where the build tree is in the mounted repo, `python3 -m http.server -d build_web_wasm32_debug/examples/openglcore 8000` and `http://localhost:8000/ControlTest.html?control=ButtonDemo&scale=2`, or `OpenGLCore.html?demo=ColorPickerDemo`. An argument the exe does not take ends the run as natively, its usage on stderr (shown in the page's `#output` panel) and exit status 1. In the window, ControlTest exports, for a script driving the page (`Module.ccall(name, 'string')`, `-sEXPORTED_RUNTIME_METHODS=ccall`), `gweni_web_bounds_listing` (the window canvas's `--dump-bounds` listing as it is now, labelled and sized as a capture's) and `gweni_web_focused_text` (the keyboard-focused Label's text); both apps export `gweni_web_depth_view(on)` (1 opens the window canvas's depth view, 0 closes it, anything else only reads; returns `view=open|closed`, OpenGLCore's with ` button=on|off rect=x,y,w,h` of the shell's Depth button), and ControlTest calls the page's `Module.gweniDepthViewChanged(open)`, if it set one, whenever the view opens or closes. Under `__EMSCRIPTEN__` the headless path is `capture.h`'s `GWENI_EXAMPLE_WEBGL`: `capture::initEglContext` (the EGL path's name, so the apps' `--headless` and `tests/main.cpp` take it unchanged) makes a WebGL 2 context on `#canvas` with `emscripten_webgl_create_context` (depth on, no antialias, never refused as a "major performance caveat") and reports it to the page (`Module.gweniWebGLContext`). `vcpkg.json` has `glew` and `glfw3` as `"platform": "!emscripten"`, and keeps vcpkg's `freetype` (not Emscripten's port) so the SDF module and the version match native. On the web, `platform::getExecutableDir()` is `/`, the root the resources are preloaded under (`/resources`), `platform::setCursor` sets the CSS `cursor` of the page's canvas (`Module.canvas`, which `pre.js` sets to `#canvas`; `default`, `text`, `pointer`, `ns-resize`, ...), and the file dialogs print one line on stderr the first time they are used (`source/platforms/crossPlatform.cpp`: they return cancelled), and the clipboard is the browser's in the interactive page and an in-process buffer in a headless page capture, which says so once on stderr when it is used: `input::GLFW3::useSystemClipboard` calls `platform::useBrowserClipboard`, gweni's own `copy`, `cut` and `paste` listeners on `window` in the capture phase, ahead of emscripten-glfw's (whose paste is the text of the paste before the keystroke, and whose copy writes `' '` with no DOM selection), so a Ctrl+C or Ctrl+X is written in the copy or cut event that follows its keydown, a `setClipboardText` from a click (a Copy button: it must come from an input handler, the browser's user activation) through `navigator.clipboard.writeText`, and a Ctrl+V pasted from the paste event of that keystroke, `Module.gweniClipboard` recording which (`docs/architecture.md` → "The clipboard"). The URL, history, opener, storage and names of `platform.h` are the browser's in a page (`crossPlatform.cpp`'s `EM_JS` functions; under node, which has no `window`, the in-process ones every other target uses): `currentUrl()` is `location.pathname + location.search + location.hash`, `pushUrl`/`replaceUrl` hand the whole resolved path to `history.pushState`/`replaceState` made absolute against `location.href` (so a `<base href>` changes nothing), the URL-changed handler runs from a `popstate` listener calling the exported `gweni_platform_url_changed`, a task of its own between frames (`history.back()` delivers it on a later task), `openUrl` is `window.open(url, '_blank', 'noopener,noreferrer')` (which returns null opened or blocked, so a blocked popup is not reported; one opened from a click or a key has the user's activation), storage is `localStorage` (a write over the quota returns false) and `setStorageFile` does nothing, and the names are `Intl`'s zone and `navigator.language`. `tests/webPlatform.cpp` pins them in `gweni_unittests.html` (its cases compile only under `__EMSCRIPTEN__`). A page served at every path (`/app/...`) must load its script absolutely or set `<base href>`, since Emscripten finds the `.wasm` and `.data` next to the script; gweni's own pages stay relative (`docs/architecture.md` → "The URL, history, links and storage"). The vcpkg binary cache starts cold for `wasm32-emscripten`: the first configure builds its ports (about 30 s on 32 cores), and they are cached like the native ones after that.

Two layout bugs only wasm32 showed, both fixed and both invisible on x86-64:
- `json.h`'s `returnValue` specialised `size_t`, which is `uint64_t` on x86-64 but not on wasm32, so the skin's `getVector<uint64_t>` hit the `assert(false)` template. It now specialises `unsigned int`, `unsigned long` and `unsigned long long`.
- freetype-gl was built with `FREETYPE_GL_USE_VAO`, which adds a field to `vertex_buffer_t`, while gweni included the header without it. On x86-64 the field fits in padding. It is now a PUBLIC definition of the `freetype-gl` target.

**`tests/web/run.mjs`, the browser runner**: `node tests/web/run.mjs [--out <dir>] [--mount <dir>:<path>]... [--timeout <s>] [--no-swiftshader] [--no-webgl2] [--quiet] <page.html> [-- <args>...]`.
- It serves the page's directory on a loopback port and opens the page in the image's headless Chromium with `<args>` as argv (each an `argv=`).
- `--mount` copies a host directory into the page's file system before `main` (`addInitScript` → `window.gweniMounts`, written in `preRun`).
- It waits for the run to end: returned, `exit()`ed, aborted, or an uncaught exception, which stops the wait at once.

- `runPage()` and `parseArgs()` are exported for scripts that check what a run wrote (`tests/web/shot.mjs`).

### Benchmarks and profiling

`gweni_bench` (`bench/`, built with `GWENI_BUILD_TESTS` and `GWENI_BUILD_EXAMPLES`, into `build_linux_x64_<type>/bench/`, with its own copy of `resources/` next to it, mirrored like the examples' by `cmake/mirrorDirectory.cmake`) measures what a frame costs on the full path: gweni, the textured skin and `OpenGLCore` on a surfaceless EGL context, or with `--renderer vulkan` (`GWENI_RENDERER`) `renderer::Vulkan` on a headless Vulkan device (always headless; it never opens a window). The two give the same counters but `allocs_flush` (and so `allocs`/`alloc_bytes`) with the validation layer on (`GWENI_VULKAN_VALIDATION=1`), whose own allocations it counts. It is for weighing a change, not a gate, with one exception: `bench_scaling` fails when a `scaling=local` scene does more work per frame at N=10000 than at N=1000, on exact counters, never on a time ("Tests").

```bash
mm run --lock render --lock quiet -- build_linux_x64_release/bench/gweni_bench --scene hover-sweep --n 10000
build_linux_x64_debug/bench/gweni_bench --list     # the scenes: name takes_n= default_n= warmup= frames= scaling= description
build_linux_x64_debug/bench/gweni_bench --help     # options and every output key
```

It runs one **scene** (`--scene`), a tree built in code (not a Demo page, so a page can change without moving the numbers) with the input or edits it drives each frame: `build` (an N-item mix of Labels, Buttons, TextBoxes, CheckBoxWithLabels in nested ScrollControls, a ListBox and an expanded TreeControl, under a bold title Label, the tree's second font; its first frame), `idle` (that tree settled, no input), `hover-sweep` (the mouse one row down a ListBox of N rows per frame), `set-text` (`--k` of N Labels, default 10, get a new string of the same length per frame), `type` (a letter typed, every fourth frame a Backspace, in the middle of a focused TextBoxMultiline of N words, a paragraph per 12), `scroll` (the wheel one notch per frame over a fixed-size ScrollControl of N 30-unit Button rows, down to the end and back up; a notch is `30*(1 - viewable/content)` units, about one row at large N), `vlist-variable-scroll` (the wheel one notch down per frame over a 400-wide VirtualList in variable mode of N wrapped rows of one to five lines, the idle re-measure off, so a frame measures only the items it brings into view), `drag` (a Window of a fixed 40 controls dragged by its title bar over N Labels, pressed in the last warm-up frame and released in the last measured one), `tree-toggle` (a 50-leaf node near the top of an expanded N-node TreeControl collapsed and expanded in turn), `tree-relabel` (a closed TreeControl node holding N rows given a new label of the same length per frame), `add-remove` (the oldest of N Labels deleted, outright and with `delayedDelete()` in turn, and a new one added, per frame), `bring-to-front` (the next of 8 cascaded Windows holding N Labels between them brought to the front), `resize` (the build tree, the canvas, target and view between 3/4 of `--size` and `--size`), `scale` (the build tree at `Canvas::setScale` 1.5, 2 and 1 in turn, the target resized to match), `nested-resize` (N Labels docked Top in containers nested `--k` deep (default 8), each docked Center in the one above, the innermost and every third one out from it a vertical ScrollControl, the canvas, target and view resized as in `resize`: a resize at depth K, about one `invalidations` and three `layout_visited` per control at any K) and `animate` (`--k` indeterminate ProgressBars and a focused TextBox's blinking caret among N idle Labels, no input; the caret is lit for 1.5 s after the focus, so it warms up 90 frames), `hidden-pages` (a header row of 20 Buttons built first, `--k` pages (default 10) holding N Buttons between them, hidden after the first frame as a TabControl leaves the pages switched away from, and a footer row of 20 built last, so the 40 shown slots are at both ends of the mirror; each frame hovers the next header Button) and `code-edit` (a CodeEditor with line numbers, highlighted as YAML, over a generated N-line YAML document, each line a function of its index, the caret before the `:` of a top-level key at line 500, or N/2 below N=1000, 20 lines down the view, so the strings and numbers on screen are the same at any N; each frame one edit there in a cycle of 10: letters, Return, a Backspace joining the lines, letters, Ctrl+Z, a letter, End and ` |` opening a block scalar over the key's 7 lines, and two Backspaces and Left closing it), `code-edit-wrap` (code-edit's first 8 edits, with no block scalar and no language, at the end of a long note line near line 500 of a wrapped CodeEditor over N 8-line blocks, one a note wrapping into two or three rows: the letters lengthen a wrapped line, now and then a row more moving the rows below, Return and Backspace insert and remove a list item; no line numbers, whose gutter width follows the line count's digits and would make the wrap depend on N, the idle re-measure off, and the caret's line 3 lines above the viewport's bottom, so a Return scrolls nothing and the render drain's queue stays far under its tree-walk threshold), `code-scroll` (that editor scrolled one line a frame, `scrollByRows(1)`), `log-append`, `log-append-detached` and `log-append-capped` (a 600x300 LogView pre-filled with N rows, each a function of its distance from the end so the rows on screen are the same strings at any N, taking 17 rows a frame, 1000 a second on the stepped clock: following; scrolled 300 rows up, a frame writing the thumb's slot and the jump button's count alone; and following at a cap of 2000, filled up to it below N=2000, one row dropped per row appended; 300 high so the thumb is at its least length and moves on no frame; their `allocs_input` is in `bench_scaling`'s EXCLUDED with #659, the height index's leaf splits landing on frames set by N mod 128), `hidden-gaps` (N Buttons, all hidden after the first frame but every (`--k`+1)-th, so the slots are runs of one shown slot between gaps of K hidden ones, no input after that; what `--range-gap`/`--range-cap` were measured with, #508), and four on a NodeGraph filling the canvas at zoom 1 with N nodes (default 300: a title, two pins and a Label body each, in a grid of ceil(sqrt(N)) columns below an empty band, each output Bezier-linked to the next node's input in its row): `graph-drag` (the first node dragged by its title bar, pressed in the last warm-up frame and released in the last measured one), `graph-marquee` (a marquee from the empty band grown over the first node and its link, held: the release's hover hit-test walks every node and link, with no spatial index in v1), `graph-pan` (a right drag) and `graph-zoom` (a wheel notch in and out in turn), `chart-append` (a point appended per frame to a Chart's line of N points in a fixed x and value range, the legend off: two slots written and nothing laid out at any N, though the renderer walks every point) and `timeline-hover` (the mouse onto another bar per frame of a Timeline of N bars over 100 lanes in a fixed day: the hover look's one slot written, the hit test the lane from y and a binary search of its bars). Each scene is **`scaling=local`** or **`scaling=linear`** (`--list` and the summary line): a local scene (`idle`, `hover-sweep`, `set-text`, `type`, `vlist-variable-scroll`, `drag`, `tree-relabel`, `add-remove`, `animate`, `hidden-pages`, `code-edit`, `code-edit-wrap`, `code-scroll`, `log-append`, `log-append-detached`, `log-append-capped`, `graph-drag`, `graph-marquee`, `chart-append`, `timeline-hover`) changes a fixed part of the tree each frame, so its per-frame counters must be the same at any N (a counter that grows is a finding: `bench_scaling` fails on it, and the scaling check of `tools/bench.sh` reads this); a linear one touches every control by design (`build`; `bring-to-front`, whose moved Window takes new z for all of its N/8 Labels; `resize`, whose layout is local now (#578: 20 entries and 7 invalidations a frame at any N) but whose canvas clip region changes, so every control is rendered again; `scale`, a relayout of everything; `nested-resize`, where every container and Label gets a new width; `scroll`, where every row moves; `tree-toggle`, where every node below the toggled one moves; `graph-pan` and `graph-zoom`, where every node's slots move). `draw_calls` (one per index chunk of 16383 slots with a slot that shows), `primitive_slots_drawn`, `primitive_ranges` and the idle frame's `flush_us` grow with the shown N in every scene but `hidden-pages`, whose shown part is fixed: every frame draws every chunk's runs of slots that can show. `--draw-slots every` draws every slot of the mirror instead (`setDrawEveryPrimitiveSlot`, the reference), and `--range-gap G --range-cap R` set the ranges' limits (`setPrimitiveRangeLimits`); one not given keeps the renderer's own, `GWENI_PRIMITIVE_RANGES` or else 2 and 16. `--n`, `--k`, `--frames` (measured), `--warmup` (run first, not reported) default per scene; `--size WxH` (default 1280x800, scale 1), `--resources <dir>`, `--json`. A new scene is a `bench::Scene` subclass and one row in `scenes()` (`bench/scenes.cpp`) with its `Scaling`; its `step(ctx, frame)` gets the warm-up frames as `-warmup..-1`, `ctx.frames` is the measured count, and `ctx.setTarget(size, scale)` resizes the canvas, the offscreen target and the renderer's view as a window's callbacks do.

The output, the interface the scripts parse: one line per measured frame, `scene=<name> n=<N> frame=<i>` then `key=value` pairs, and one `summary` line (`--json`: the same as one object, `frames` and `summary`). Per frame, the wall time of each **phase** in microseconds: `input_us` (the scene's step), `update_us` (`updateCanvas()`), `render_us` (`renderCanvas()` without the renderer's `end()`), `flush_us` (the renderer's `end()`, which is `SlotRenderer::flush()`: the slot diff, the uploads and the draws, split off by `TimedFlush<Renderer>`, a wrapper subclass in the bench that takes any backend, so the renderer is unchanged) and `gpu_us` (a `glFinish()` after the frame, `vkQueueWaitIdle` on Vulkan, `capture::Device::finish()`; in the container that is Mesa llvmpipe or lavapipe rasterising on the CPU, `renderer=` (the backend) and `device=` (`GL_RENDERER`, or the Vulkan device's name) in the summary say which, and it is not a GPU's cost). Then the **counters**: `ChangeStats` (`visited`: the queued controls the render phase rendered, `render_carried`: the queue entries it left for a later frame, `controls_changed`, `created`, `visibility`, `geometry`, `background`, `text`), `FrameStats` (`prim_slots_written`, `text_slots_written`, `upload_calls`, `upload_bytes`, `mirror_bytes`, `draw_calls`, `primitive_slots_drawn`: the primitive slots the frame's draws covered, its runs of slots that can show with their merged gaps, `primitive_ranges`: those ranges, `text_draws`, `atlas_upload_calls`, `atlas_upload_bytes`, `buffer_regrows`: the vertex buffers and clip-box textures the mirror outgrew, each re-allocated and sent whole once), `LayoutStats` (`layout_passes`, `layout_capped`, `render_layout`, `layout_visited`: the controls the frame's layout passes entered, one per `calculateSize()` and one per `arrange()` in each axis, `layout_children_scanned`: the children their generic loops went over, entered or not, `LayoutStats::childrenScanned`), `measure_calls` (the renderer `measureText()`, `lineHeight()` and `measureCarets()` calls the controls made in the frame, every one through `Base::measureText()`, `Base::measureLineHeight()` or `Base::measureCarets()`, counted by `controls::measureTextCalls()`) with `measure_calls_input`, `_update` and `_render`, its share in each phase (an edit of a wrapped `Text` wraps in the input phase, where `TextBox::insertText` asks for the caret's place; `LayoutStats::measureCalls` is the update and render-phase layout's), `invalidations` (the `Base::invalidate()` calls of the frame, each step of one's walk up to the canvas a call, counted by `controls::invalidateCalls()`, none from a `setExcludedFromStats()` subtree or a control with no parent that is not a canvas; a scale change is one per control plus the root's depth, `docs/layout.md` → "Invalidating a whole subtree"; a new size one per child of the resized control, plus its way up to the canvas outside a layout pass, → "A new size invalidates the children", "No way up in a pass") with `invalidations_input`, `_update` and `_render`, `z_visited` and `z_changed` (`UpdateStats::zVisited`/`zChanged`: the controls the z renumber entered, and those whose z it changed), `anims_run` (`UpdateStats::animsRun`, the animations the update phase ran), `hit_tests` (the controls the frame's hit tests entered, one per `controls::Base::getControlAt` call, the hover's included: the running `input::hitTestVisits()`, which is never reset, diffed over the frame), the live `prim_ids`/`text_ids`, and `allocs`/`alloc_bytes` with `allocs_<phase>`: C++ `operator new` calls on the main thread (the bench replaces the global one, `bench/allocCounter.cpp`; C `malloc`, e.g. freetype-gl's, and Mesa's own threads are not counted). The summary has `scaling=` (the scene's, as `--list` gives it), `controls=` (every control in the tree after the last frame), `construct_us`/`construct_allocs`/`construct_invalidations` (`Scene::build()`), `<phase>_us_min/_median/_max` and `<counter>_total/_max`.

The same arguments always give the same counters, and only the times vary: the clock is stepped 1/60 s per frame (`platform::setTimeSource`), the input is the scene's own, and before the scene is built a primer canvas (a small `build` tree) draws two frames and is deleted, so llvmpipe has compiled its shader variants before the measured frames (LLVM's allocations while compiling differ from run to run, and Mesa's on-disk shader cache changes them again). The font atlas's first upload therefore happens in the primer too, not in `build`'s frame. Times come from a release tree. Hold the `render` lock around a run, as for any capture, and `quiet` too when its times matter (`mm run --lock render --lock quiet -- ...`, one run each); a run read only for its counters needs `render` alone. To see where a scene's instructions go, profile it ("Profiling a scene"); to weigh a change, compare it with its base ("Comparing two revisions"). `bench_smoke` (`bench/smoke.cmake`, label `gpu`) runs every scene in `--list` at N=50 for 3 frames and fails, naming the scene, only if one exits non-zero, crashes or prints the wrong lines; `bench_smoke_vulkan` (labels `gpu`, `vulkan`) runs it on Vulkan, validated.

### Profile tree

`./generate.sh linux profile` configures `build_linux_x64_profile/`: `CMAKE_BUILD_TYPE=RelWithDebInfo` (`-O2 -g -DNDEBUG`) with `-DGWENI_FRAME_POINTERS=ON`, which adds `-fno-omit-frame-pointer` to everything built here, the vendored `deps/` included (set before `deps/` is added, as the sanitizers are). It is the tree to profile and to compare revisions in: optimised like a release build, but with the line tables callgrind's per-line annotation needs and frame pointers a stack-walking profiler needs. The toolchain, triplet, examples and tests are those of every other tree, and its tests pass like theirs, `docs_samples` included (it renders the same bytes). `profile` is its own build type, so `./generate.sh linux profile release` and `./generate.sh linux profile asan` print one error and exit 1.

```bash
./generate.sh linux profile
cmake --build build_linux_x64_profile -j
mm run --lock render -- ctest --test-dir build_linux_x64_profile -L gpu
ctest --test-dir build_linux_x64_profile -LE gpu
```

The image (`Dockerfile`) has the profiling tools: `valgrind` (callgrind, `callgrind_annotate`, and `<valgrind/callgrind.h>` for client requests), `graphviz` (`dot`) and `gprof2dot` (from PyPI, pinned, since Ubuntu 22.04 does not package it). A container built from an image older than that change lacks them: `which valgrind gprof2dot dot` tells. From a host, `./run_docker.sh -r` rebuilds the image.

### Profiling a scene

`tools/profile.sh` runs one `gweni_bench` scene under callgrind and shows where its instructions go, per phase, per function and per line of gweni's sources. It needs the profile tree and the image's valgrind, gprof2dot and dot (see "Profile tree"), runs from any cwd and takes no lock: callgrind counts instructions, with llvmpipe on the main thread (`LP_NUM_THREADS=0`), and the count is the same however busy the host is. Its one lock is a local `flock` on its staging directory (below):

```bash
tools/profile.sh hover-sweep --n 1000                 # writes /tmp/gweni-profile-hover-sweep-1000/
tools/profile.sh build --n 10000 --out /tmp/build10k  # --frames F, --bin-dir DIR, -- <more gweni_bench args>
tools/profile.sh hover-sweep --graph-root gweni_bench_phase_input --graph-thres 0.01
```

It writes into the out dir (default `/tmp/gweni-profile-<scene>-<N>`; its old outputs are replaced): `callgrind.out`, the profile, to open on a host with `kcachegrind`/`qcachegrind` (the paths in it are the container's, so point it at the repo for the sources) or to read with `callgrind_annotate`; **`phases.txt`**, the instructions of each phase, one `phase=<name> ir=<n>` line for `construct` (the `build` scene's `Scene::build()`, 0 in every other scene), `input`, `update`, `render` (without the flush), `flush`, `gpu` and `other` (the few instructions collected outside every phase), then `total ir=<n>`, which they add up to exactly, the interface `tools/bench.sh` reads (`tools/callgrind_phases.py` computes it); `annotate.txt`, the phases, the list of gweni's own files (`source/`, `include/`, `bench/`) the profile has costs in, the functions by inclusive cost and those files line by line (`callgrind_annotate --inclusive=yes`: a line's cost is its own instructions plus those of the calls it makes, so a line calling into Mesa shows that cost; a recursive function's second level is `name'2` and can show more than 100 %); `callgraph.svg`, gprof2dot's call graph coloured by inclusive share, hot paths red, of the functions with at least 0.5 % of the profile (`--graph-thres P`, the calls at P/5; `--graph-root FN` keeps FN and what it calls, still as shares of the whole profile; a small P gives thousands of nodes and `dot` takes minutes); `bench.txt`, the bench's own output (counters as always, times about 50x a real run); and `valgrind.log`. A run takes about 20 s for `build --n 10000`, 1-2 min for `hover-sweep --n 1000` (20 frames, nearly all of it llvmpipe rasterising) and `set-text --n 1000`, and about 100 s for `type --n 1000`.

Only the measured work is in the profile: the measured frames and the `build` scene's construction. Valgrind starts with `--instr-atstart=no --collect-atstart=no` and the bench switches both with client requests (`bench/callgrind.h`; built in when `<valgrind/callgrind.h>` is there, no-ops otherwise, and `-DGWENI_BENCH_NO_VALGRIND` leaves them out): `setCollecting()` instruments the construction and the measured frames, and `enterPhase()` collects while a phase runs, so EGL and GL init, the skin, fonts and resources, the shader primer, warm-up frames, `glClear`, the bench's bookkeeping and teardown are absent (collection alone would keep their costs out but still count their calls at call sites the frames share). Each phase's work runs inside a marker function of its own, `gweni_bench_phase_<name>` (`bench::inPhase`), and a phase's instructions are its marker's inclusive cost, exactly; the flush marker runs inside the render one (the renderer's `end()`), so render is the difference. One collection keeps one profile for every tool; a part per phase (`CALLGRIND_DUMP_STATS_AT`) would give the totals too, but as hundreds of parts that `callgrind_annotate` and gprof2dot do not merge.

The counts are the same every run, to the instruction, for the same binary, scene and arguments, whatever the cwd, the environment or the path the binary was built at. Everything that moves the stack or the heap is fixed: the script copies `gweni_bench` to `/tmp/gweni-profile-run/` (so `argv[0]` and `/proc/self/exe` are the same), links the resources in beside it and runs it there with `--resources resources` (so every path the bench builds has the same length), under `env -i` with only `PATH`, `HOME` (the stage dir, which has no `.drirc`), `LIBGL_ALWAYS_SOFTWARE=1` (the image's pin, which `env -i` would drop), `LP_NUM_THREADS=0` (llvmpipe rasterises on the main thread), `MESA_SHADER_CACHE_DISABLE=true` and `GLIBC_TUNABLES=glibc.malloc.mxfast=0:glibc.malloc.tcache_count=65535:glibc.malloc.mmap_threshold=131072`. Runs on one host take turns on the stage dir (`flock` on `/tmp/gweni-profile-run.lock`), so a `--resources` among the extra bench arguments must be absolute. Under valgrind the bench's own `getrandom()` (`bench/fixedRandom.cpp`, the one symbol the exe exports, `bench/exports.list`) hands out a fixed sequence: expat, which Mesa parses its drirc files with, salts its hash tables from `getrandom()`, and with a random salt the phases moved by a few percent from run to run (`build --n 1000`: `update` from 191.9 M to 197.7 M over 10 runs). Outside valgrind it is the system call.

**Layout noise between two binaries.** How much work glibc's malloc does depends on how the heap is laid out (consolidating fastbins, searching its bins), and two revisions of the bench lay it out differently even where gweni does the same work. With glibc's default settings, lengthening the stage dir's name alone (which lengthens the resource paths) moved `build --n 10000`'s `update` from 1879.5 M to 1932.5 M (2.8 %) over six lengths, and with fastbins off but the rest as it is, from 1895.6 M to 2015.2 M; hence the tunables, with which every small free stays in the thread cache and nothing is consolidated. `--layout-pad K` runs from a stage dir K characters longer, so a few runs at different K sample this noise. Measured with K = 0, 16 and 63 (and 7, 32 and 129 for `build`):

| scene | phase | range over K | spread |
|---|---|---|---|
| `build --n 10000` | construct / update / render / flush | 216.00-216.07 M / 1851.5-1858.2 M / 443.03-443.27 M / 241.015-241.024 M | 0.03 % / 0.36 % / 0.05 % / 0.004 % |
| `hover-sweep --n 1000` | input, update, render / flush | identical / 4334.85-4335.00 M | 0 / 0.004 % |
| `set-text --n 1000` | input / update / render / flush | 373.28-373.38 K / 1551.0-1552.4 M / 11.969-11.974 M / 2804.39-2804.54 M | 0.03 % / 0.09 % / 0.05 % / 0.005 % |
| `type --n 1000` | input / update / render / flush | 3583.6-3584.0 M / 891.49-891.60 M / 4.723-4.726 M / 5495.94 M | 0.01 % / 0.01 % / 0.07 % / 0 |

So a difference of under 0.4 % in `update` and under 0.1 % elsewhere between two revisions can be layout alone. glibc's share of the counts is that of this malloc configuration, not of the default one.

With `LP_NUM_THREADS=0` llvmpipe rasterises inside the `glFlush()` that ends `SlotRenderer::flush()` (`OpenGLCore::submitFrame()`), so under callgrind that cost is in `flush` and `gpu` (the `glFinish()`) is nearly nothing, while in a timed run llvmpipe's threads rasterise and `gpu_us` waits for them. Either way it is Mesa's CPU rasteriser, not a GPU's cost. Mesa's own functions are anonymous `???:0x...` in `swrast_dri.so` (the image has no symbols for it), and its JIT-compiled shaders `???:0x...` in no object at all. In a local scene that is nearly the whole profile, so gweni's own share is `input`, `update` and `render` in `phases.txt` and its lines in `annotate.txt`.

### Comparing two revisions

`tools/bench.sh compare <base-rev> [<rev>]` weighs a change: it builds both revisions, runs every `gweni_bench` scene on each and writes one markdown report of how the work counters, the instructions (callgrind) and, with `--time`, the wall time moved, per scene and phase. It flags what got worse and nothing else; it is not a gate, there is no checked-in baseline (the baseline is always the base revision), and it exits 0 whatever the report says, 1 only when a build, a run or a tool failed (naming the step on stderr), 2 for a bad argument. Inside the container, from any cwd:

```bash
tools/bench.sh compare origin/main                       # origin/main vs the working tree, uncommitted changes included
tools/bench.sh compare origin/main --keep                # keep origin/main's export and build for the next compare
tools/bench.sh compare HEAD~3 HEAD --scenes hover-sweep,type --no-ir
tools/bench.sh compare origin/main --time --repeat 5     # wall time too
```

Options: `--scenes a,b,...` (default every scene either side has), `--n-small N`/`--n-large N` (1000/10000: the counters run at both), `--ir-n N` (the N callgrind runs at, default the small one), `--no-ir`, `--time`, `--repeat R` (timed runs per scene and side, default 5), `--time-n N` (default the small N), `--out FILE` (default `/tmp/gweni-bench-<base>-<rev>.md`; the raw outputs go into `FILE` without `.md` plus `.d`), `--keep`. **When to run it:** before finishing a change to `source/` or `include/`, run `tools/bench.sh compare origin/main` (no `--time`) and look at its flags; accept each one in the task's report or fix it. Run `--time` when asked to.

**The sides.** A commit is exported with `git archive` (not `git worktree add`: the slots share one repository, and an export registers nothing in it and leaves nothing to prune if the run is killed) to `/tmp/gweni-bench-src-<sha>/` and built there in its profile tree (`./generate.sh linux profile`, `cmake --build ... --target gweni_bench`). An export that is already there, from an earlier `--keep`, is reused and left in place, so repeated compares against one base build it once; one made by this run is removed at the end unless `--keep`. The working tree (the default `<rev>`) is built in its own `build_linux_x64_profile/`, in place, so its uncommitted changes are measured without copying them and an existing profile build of it is reused incrementally. Each new export configures from scratch, which restores the vcpkg dependencies from the binary cache: quick with `/vcpkg-cache` mounted, slow (the whole dependency build) when `VCPKG_DEFAULT_BINARY_CACHE` is unset. A side with no `bench/` (a revision from before `gweni_bench`) is not built, and every scene is reported as new; a side from before the profile tree is built as its release tree, and the report says so.

**The runs.** Every `gweni_bench` run is that side's binary copied to `/tmp/gweni-bench-run/gweni_bench` and run from there with its own resources linked beside it (`flock` on `/tmp/gweni-bench-run.lock`, so the runs of two compares in one container take turns on the stage dir, one run at a time), in `env -i` with `PATH`, `HOME`, `LIBGL_ALWAYS_SOFTWARE=1` and `MESA_SHADER_CACHE_DISABLE=true`, so where a side was built changes nothing it does; a counter run adds `LP_NUM_THREADS=0`, a timed one leaves llvmpipe its threads. The instructions are this checkout's `tools/profile.sh --phases-only` (which writes `callgrind.out`, `phases.txt` and `bench.txt`, and no annotation or graph) run on each side's binary, so both sides are measured by one harness. Each run takes its locks on its own, never one lock around the batch: a counter run `mm run --lock render` (it opens a GL context, on llvmpipe), a timed one `mm run --lock render --lock quiet`; `quiet` waits until no other job holds a lock and keeps them off while the run lasts, and is held for one run of about a second, never longer (a hold over 10 min would take it over). The callgrind runs take no lock: instruction counts do not depend on the host's load. Without `mm` on `PATH` everything runs unlocked and the report says so. Builds hold no lock.

**The report.** A summary at the top: the two commits, the sizes, how long each step took, whether `bench/` differs between the sides (`git diff --stat` of `bench/`, untracked files included: a changed scene moves its numbers by design), the flag count of each section with the worst ones, the scenes on one side only (`new`/`removed`) and any notes (unlocked runs, a side without a bench or a profile tree). Then:
- **Counters**: every counter of every scene at each size, its per-frame `median`, `max` and `total` over the measured frames (and the summary's `controls`, `construct_allocs`, `construct_alloc_bytes` and `construct_invalidations` as `run`), base → rev with the exact delta. The counters are deterministic, so **every value that differs is flagged** ⚠; unchanged values are collapsed into one line per scene, with their count.
- **Instructions**: each phase of `phases.txt` per scene at `--ir-n`, base → rev, delta and %, flagged when it is **more than 1 % above the base** and at least 0.1 % of the scene's total (so `gpu` and `other`, a few hundred instructions under callgrind, are shown but not flagged). 1 % is above the layout noise between two binaries that "Profiling a scene" measured (under 0.4 % of `update`, under 0.1 % elsewhere). Fewer instructions are shown, never flagged. Most of a local scene's count is llvmpipe rasterising inside `flush`, so a gweni change shows in `input`, `update` and `render`.
- **Scaling**: for each `scaling=local` scene, every per-frame counter (median and max) at `--n-large` against `--n-small` on rev. A counter that grows there and did not on base is a **new O(N)**, flagged and listed first; one that already grew on base is listed as known, unflagged, and one that grew on base only as fixed. `prim_ids`, `text_ids` and `mirror_bytes` are sizes and left out; `draw_calls` and `text_draws` grow with the slot count in every scene (one draw per index chunk of 16383 slots) and are never flagged; `primitive_slots_drawn` and `primitive_ranges` follow the shown slots and are never flagged either, but in `hidden-pages`, where they are pinned as in `bench_scaling` (`PINNED` in `tools/bench_report.py`) and any change between the sizes, up or down, is a new O(N). The `linear` scenes are listed with the growth factor of their per-frame `visited`, `z_visited`, slots written, upload bytes and allocations.
- **Wall time** (`--time` only): `--repeat` rounds at `--time-n`, each round running every scene once per side, base and rev taking turns going first (A B in one round, B A in the next), so a scene's runs are spread over the whole timed part and a burst of load lands on one of them rather than on all of one side's. A run's phase time is its median over the measured frames (`construct` the build itself); the table gives the median of the runs ± their MAD (median absolute deviation, which one slow run does not move as it would a standard deviation), flagged when rev is **more than 5 % slower, slower by more than twice the larger side's MAD and by at least 2 µs** (below that a phase is timer noise). `gpu` is marked: it is llvmpipe rasterising on the CPU, not a GPU's cost. The builds are the profile trees (`-O2`), as for every other number here.

How long it takes (measured on localworker, 13 scenes, the vcpkg cache mounted): exporting, configuring and building a base about 30 s (the working tree's incremental build seconds); the counters 1-2 min (more when the `render` pool is full: each run waits for a place); the instructions about 38 min, about 1 min per scene and side under callgrind (`build` 10 s, `bring-to-front` 2 min), so **a default compare takes about 40 min**, and `--no-ir` about 2 min. `--time` adds about 1.5 min at `--repeat 5`. To weigh a change to one path quickly, `--scenes` the scenes that exercise it.

**How far to trust a wall-time flag.** `compare HEAD --time --no-ir` on a clean tree (two binaries with byte-identical `.text`, every timed run holding `render` and `quiet`) flagged 2 of its 78 scene phases in each of two runs on localworker, different ones each time: `hover-sweep` flush +6.1 % and `scroll` construct +9.0 %, then `set-text` flush +17.0 % and `resize` gpu +6.9 %. `quiet` keeps every other locked job off the host while a run lasts, but builds take no lock (the load average stayed at 3 to 4 while other agents compiled), and llvmpipe's rasteriser threads vary on their own. So a wall-time flag is a reason to run again, with a larger `--repeat` or `--scenes` the flagged ones, not a verdict; the counters and instructions, which do not depend on the host's load, are. (Before the runs held `quiet`, the same compare flagged 1 to 5 phases per run, up to +56 %.)

`tools/bench_report.py <results dir>` writes the report from the raw outputs, so it can be rerun on a `.d` dir after a change to the report alone; its header lists the files it reads.

## Architecture

> Full write-up in [`docs/architecture.md`](docs/architecture.md); summary below.

### Core goal: API-agnostic, change-tracked UI
The whole point of gweni is that **UI logic (layout, padding, docking, hover/highlight/focus, hit-testing) is decoupled from the rendering API**. The same control/skin code is meant to drive OpenGL today and Vulkan (or any backend) later, by implementing one abstract interface — `gweni::renderer::Base` (`include/gweni/platforms/baseRender.h`). The core never makes API calls directly; it only calls that interface. `OpenGLCore` is the shipped backend, and it is split in two: `renderer::SlotRenderer` (`include/gweni/platforms/renderers/slotRenderer.h`) holds everything API-independent (the CPU vertex and clip-box mirrors and their per-slot diff, the vertex packing, the text runs and draw lists, font resolution and layout over the CPU-side atlases, the images, `FrameStats`, all counted there), and `OpenGLCore` implements its pure-virtual backend hooks (buffer and clip-box allocation and range uploads, atlas and image textures, one draw per chunk, the frame's begin and submit; `docs/architecture.md` → "The shared core: `SlotRenderer` and its backend hooks"), so another backend implements those hooks and nothing else, as `renderer::Vulkan` (`include/gweni/platforms/renderers/vulkan.h`, built with `GWENI_RENDER_VULKAN`) does: every primitive style and text in every mode, headless or in a window with a swapchain, drawing into an application-owned `VulkanTarget` in GL's window coordinates with GL's shader bodies (`source/platforms/renderers/shaders/*.glsl`, compiled to SPIR-V behind `source/platforms/renderers/Vulkan/primitive.{vert,frag}`), so its pixels are GL's (`docs/architecture.md` → "renderer::Vulkan (headless)"); `StubRenderer` (`tests/unit/headlessFixture.h`) is a second implementation of `renderer::Base`, compiled in every build with tests on (the default), so the interface stays implementable outside OpenGL.

The frame is two phases (`examples/openglcore/openglcore.cpp`):
1. **`canvas->updateCanvas()`** — logic only: input, animations (`anim::think(canvas)`), layout/docking, z-order, and recording *what changed* per control as a state-change bitmask. No draw calls. It enters only what changed too, except layout: there is no per-control `think()`, a frame nothing invalidated runs no layout pass, a pass enters only the dirty paths (`Base::doCalculateSize`/`doArrange` skip a clean control; a pure move does not dirty the moved control's subtree; `layout_visited=` in `ControlTest --stats`; `docs/layout.md` → "Which controls a pass enters", issue #321), a new scale invalidates a whole subtree in one walk that enters each control once and walks up out of it once (`Base::scaleChangedSubtree()`; `invalidations=` in `ControlTest --stats`, `controls::invalidateCalls()`; `docs/layout.md` → "Invalidating a whole subtree", issue #519), a new size only the children the control holds, inner panel included, each control its arrange resizes doing the same in turn, so the canvas's resize invalidates its own children alone, and inside a pass neither walks up to the canvas (`Base::invalidateWalk(1)`; placement code in a pass walks up only to the first dirty ancestor; `docs/layout.md` → "A new size invalidates the children", "No way up in a pass", issue #578), and a parent of 16 children or more measures, places and enters only the children that changed since it last laid them out while they are under one in 16 of its children and none is docked, its size and padding unchanged (`Base::m_changedChildren`, incremental size terms in `ChildSizes`; `layout_children_scanned=`; layout verification's pass always walks them all; `docs/layout.md` → "Which children a pass enters", issue #430), and the z indices are renumbered (`Base::renumberZRecursive`: it hands z out with gaps and relabels only what the change added or moved and the few controls after it up to a free gap, `Canvas::ZGap`, and its walk enters only the path to each changed control (marked `m_zDirty` up its parent chain), a moved subtree and what an insert's cascade reaches, passing a clean subtree in O(1) by its cached end `m_zEnd`; a removal walks nothing; `docs/architecture.md` → "Gapped z labels", "Which controls a renumber enters") only on a frame after the tree order changed, which `Base` reports from `addChild`/`addChildOfLayout`/`removeChild`, `bringToFront`/`sendToBack`/`bringNextToControl` and a skin Control assigned or released (the public `Canvas::invalidateZOrder()`, for a skin Control whose counts changed on their own, makes the next renumber enter every control). The animation registry (`source/anim.cpp`) holds only animations with work to do (a focused `TextBox`'s caret blink, a cycling or indeterminate `ProgressBar`'s, a timed one until it ends), and each canvas runs, in the order they were added, only those whose control is on it, so with several canvases each runs once a frame in its own canvas's update phase; removal waits until the loop ends, so an animation may add, cancel or delete from inside its `think()`, and `anim::cancel(control, animation)` removes one alone. So a settled frame enters no control in either phase and runs no animation (`UpdateStats::zVisited` and `animsRun`, `z_visited=` and `anims_run=` in `ControlTest --stats`; `docs/architecture.md` → "updateCanvas()").
2. **`canvas->renderCanvas()`** — render: `renderer->begin()`, render the queued controls, and for each emit **only the draw-state changes needed**, then `renderer->end()`. A control with `StateChange_Nothing` issues no renderer calls. `addStateChange` (not virtual) also puts the control, once, in a process-global **pending-render queue** (`m_renderQueueIndex`; `~Base` nulls its slot), and the canvas's drain (`Canvas::renderPendingControls` → `Base::drainRenderQueue`, shared with `WindowCanvas`) renders only those on its tree, in preorder at the offset and clip the recursive walk gave them, from the root state the canvas set on the renderer: a frame with a quarter of the tree or more queued (first frame, resize, scale) or whose z ties walks the tree once; any other sorts the entries by z (the tree's preorder; a radix sort, skipped when already in order) and rebuilds each one's state down its `m_actualParent` chain, kept as a stack from one entry to the next; `renderUnder`/`render` at the parent's offset and clip, `renderOver`/`renderFocus` with the control's own offset in the parent's clip, right after it; the state cleared after its hooks. No clean ancestor's hook runs, so a look that depends on descendants is set from the update phase (`Base::onDescendantInteraction`, a `PropertyRow`'s label). A settled frame renders no control and one hover only the hovered ones (`ChangeStats::visited`, `visited=` in `ControlTest --stats`), with no sibling scanned; an entry off the canvas (detached, or on another canvas) stays queued, as does what hooks queue past the drain's cap (`ChangeStats::renderCarried`, `render_carried=`). **The walk only draws**: adding, removing, reordering or deleting a control belongs to the update phase or layout (`renderPhaseLayout()` runs before the walk, and a wrapped `Text` builds its lines there). A `Base::addChild`/`addChildOfLayout`/`removeChild` (so `setParent`)/`bringToFront`/`sendToBack`/`bringNextToControl`/`~Base` inside the walk (a `RenderWalkScope`, held by `Canvas::renderCanvas` and `WindowCanvas` around the drain only) prints `gweni: <Type>#<id> <operation> during the render walk (rendering <Type>#<id>)` on stderr once per (operation, type), in every build, and is recorded in `gweni::controls::renderWalkMutations()`; ControlTest exits non-zero if that is not empty, so `controltest_teardown` and `controltest_one_pass_each` fail on one; the drain survives such a change (it never touches a deleted control and rebuilds its stack), it only reports it (`docs/architecture.md` → "renderCanvas()").

A backend may be **immediate** (redraw everything each `drawFilledRect`) or **retained** (primitive ids index a persistent GPU buffer); the same UI code drives both. The performance target is that per-frame cost scales with what changed, not UI size.

**Threads, posts and the idle loop.** The library is one-UI-thread; the one thread-safe call is `Canvas::post(fn)` (a `gweni::PostQueue`, `include/gweni/postQueue.h`: run at the top of `updateCanvas()`, FIFO per thread and in lock order across threads, a post from a post waits for the next update; `postHandle()` for a worker that outlives the canvas, closed by `~Canvas`, after which a post returns false), with `setWakeHandler` called, from the posting thread, when the queue goes non-empty. `Canvas::after`/`every` are UI-thread timers (a min-heap run after the posts and before the animations, off the double clock `getTimeInSeconds()`; no drift, one fire after a gap; an owner's `~Base` cancels them; no animation, so nothing in `anims_run`), and `Canvas::nextWorkTime()` is when the canvas next has work (`WorkNow`, a time, or `NoWork`: posts, a redraw, queued renders, dirty layout or z, deletes, else the next timer, `anim::Animation::nextThinkTime()`, the tooltip and key-repeat deadlines). `platform::IdleLoop` (`idleLoop.h`, no window system) and `input::GlfwLoop` (`input/glfwLoop.h`, header-only, beside `input::GLFW3`; the core never links GLFW) sleep on it, and a change that touches pixels but no control must `redraw()` its canvas, which `--verify-idle` checks (`docs/architecture.md` → "Threads, posts and the idle loop").

### Namespaces & layout
- `gweni::controls` — all widgets, rooted at `controls::Base`. Headers in `include/gweni/controls/`, impls in `source/controls/`.
- `gweni::skin` — draws controls; `simple` (vector) and `textured` (atlas-based, the one the examples use) skins under `skins/`.
- `gweni::renderer` — `renderer::Base` abstract API; `renderer::SlotRenderer` (`source/platforms/renderers/SlotRenderer/`) is the API-independent part of a retained renderer, `OpenGLCore`, its GL backend, is under `source/platforms/renderers/OpenGLCore/`, and `renderer::Vulkan`, its Vulkan backend, under `source/platforms/renderers/Vulkan/`; both compile the shader bodies in `source/platforms/renderers/shaders/`.
- `gweni::platform` — OS abstractions (clipboard, cursor, file dialogs, timing, window creation) in `platforms/`, and the browser integration every target has (`platform.h`): the URL helpers (`Url`, `parseUrl`/`formatUrl`, `parseQuery`/`buildQuery`, `splitPath`/`joinPath`, `source/platforms/url.cpp`), `currentUrl`, `pushUrl`/`replaceUrl` taking only `/path[?query][#hash]`, `?query[#hash]` and `#hash` (anything else refused with one stderr line, so no resolver, `source/platforms/urlTarget.h`; a character only in the parts a browser encodes it in, so `currentUrl()`'s parts are never refused), `historyBack`/`historyForward` with `setUrlChangedHandler` (never told of the app's own push or replace), `openUrl` (http, https and mailto alone; `setOpenUrlHandler` for tests), `storageGet`/`storageSet`/`storageRemove`/`storageKeys` under `setStoragePrefix`, `timeZoneName`/`localeName`, and the clipboard: `getClipboardText`/`setClipboardText` (the call a Copy button makes) and `requestClipboardText(reply)` (a paste's read, answered inside the call or later), an in-process buffer unless `setClipboardBackend(get, set, request)` installs one (`input::GLFW3::useSystemClipboard(window)` for a GLFW app, the browser's through `useBrowserClipboard`). In a page they are the browser's (pushState, popstate between frames, `window.open` with noopener, `localStorage`, `Intl`, "Web tree"); elsewhere an in-process history stack starting at `/` whose back and forward call the handler inside the call, `xdg-open`/`open`/`ShellExecute` through fork and exec (never a shell), and a JSON file the app names (`setStorageFile`, rewritten through a temporary file and a rename; in memory with one stderr line without one). `tests/unit/browserPlatform.cpp` pins the in-process ones (`docs/architecture.md` → "The URL, history, links and storage").
- `gweni::event` — signal/slot system in `events.h`.

Public headers live under `include/gweni/...`; the directory tree there mirrors the `source/...` tree. Note the header path `include/gweni/controls/dialogs/` maps to source `source/controls/dialog/` (singular).

### The retained-primitive model (the important part)
This is what makes gweni different from upstream GWEN and is easy to get wrong:

1. Every `controls::Base` tracks a dirty bitmask via `addStateChange(...)` with flags `StateChange_Created / Visibility / Geometry / Background / Text / Caret` (defined in `controls/base.h`; `Caret` alone is a TextBox blink, which only shows or hides the caret slot). `StateChange_Nothing` means nothing to regenerate.
2. Controls own persistent renderer **primitive IDs** (`primitiveIds.h`: `getPrimitiveId`/`getTextId`/`releasePrimitiveId`). The skin's `Control` objects (`skin.h`) declare `requiredPrimitives()` and have `generate()/update()/remove()` keyed off the control's `State` (`Generate`/`Update`/`Remove`).
3. **Scale:** controls lay out in logical units, and `renderer::Base::translate()` snaps each rect's *edges* to device pixels (`Base::snap(v)=floor(v*scale+0.5)`, `w=snap(x+w)-snap(x)`), as do the clip boxes and the SDF radius/border (`max(1, snap(border))`); do not multiply by `scale()` anywhere else (`docs/architecture.md` → "Scale and the device-pixel grid").
4. `OpenGLCore` keeps to the **GL 3.3 core / GLES 3.0 / WebGL 2 subset**: no direct state access, buffer textures, `gl_PrimitiveID`, `texture2D` or `glGetTexImage` (a texture is read back through a framebuffer, `OpenGLCore::readTexture`), each stage's GLSL one body behind a `#version 330 core` or `#version 300 es` + `highp` header chosen at run time (`OpenGLCore::shaderSource`, compiled as ES 3.00 by `tests/glslDialects.cpp`), and `glMultiDrawElements` and dual-source blending only where `glCapabilities()` says the context has them (without dual-source blending LCD text is grayscale, "GLES tree"; `docs/architecture.md` → "One GL subset"). The GLES tree compiles it against `<GLES3/gl3.h>`, so the subset is checked by the compiler there. In `OpenGLCore` a **primitive id is a fixed slot in one persistent VBO**: vertices at `id*4` (`source/platforms/renderers/OpenGLCore/openglCore.cpp`). Every slot is a quad drawn through one static 16-bit index buffer of `SlotRenderer::kSlotsPerChunk` (16383) quads, so there is no index mirror; the glyph slots likewise, through a second static buffer in freetype-gl's quad order (`v, v+1, v+2, v, v+2, v+3`, so each path keeps the diagonal its quads are split along). The slots are drawn in chunks of at most that many, one `glDrawElements` each with its own vertex array pointed at its first slot (16383, not 16384: WebGL 2's fixed primitive restart at `0xFFFF`); a chunk with no slot whose style is not 0 is not drawn, and a drawn one draws its runs of such slots, a 1-slot gap merged and at most 16 ranges a chunk (`kPrimitiveRangeGap`, `kMaxPrimitiveRanges`, measured; `GWENI_PRIMITIVE_RANGES=<gap>,<cap>` or `setPrimitiveRangeLimits()` change them), as one `glMultiDrawElements` (a `glDrawElements` loop without multi-draw, as on the web; one `vkCmdDrawIndexed` per range on Vulkan), the ranges cached per chunk and built again only after a slot's visibility in it changed (`FrameStats::primitiveSlotsDrawn`, `primitiveRanges`, `primitiveRangeBuilds`, kept from the dirty slots, `docs/architecture.md` → "Only the slots that can show are drawn"). `GWENI_INDEX_CHUNK_SLOTS=<n>` (or `setIndexChunkSlots()`) makes the chunks smaller, which must draw the same pixels (`controltest_index_chunks`, `tests/indexChunks.cpp`). `update()` rewrites only that slot in the CPU mirror; unchanged controls leave their slots intact. A `Vertex` is 16 16-bit fields, **32 bytes**: `{style,x,y,z,tx,ty}` plus SDF fields `{lx,ly,radius,border,cx,cy,bx,by,dx,dy}`. `x,y` are signed device px (`int16_t`, ±32 K, with `z` an `ivec3` in the shader; `z` is `uint16_t` 0..65535, `SlotRenderer::kMaxZIndex` = `renderer::Base::maxZIndex()`, the projection's depth range, read as `inPosition.z & 0xffff`), so a rect straddling the view's top/left edge draws its on-view part; a quad with a corner outside `[-32768, 32767]` is culled by `cullOutOfRangeQuad` (all four corners at 0,0, its `style` kept), never clamped (a moved corner breaks the UV/colour/SDF interpolation and the flat half-size). Four packed RGBA pairs: `tx/ty` color0 (smooth), `cx/cy` color1 (flat), `bx/by` border (flat), `dx/dy` color3 (smooth). `style` selects the shader path (0 hidden / 1 fill / 2 image: a separately loaded image in a layer of one of 5 image pages (a 2D texture array per size class, 128 to 2048 px square, `SlotRenderer::ImageClasses`; a full page doubles its layers, `image_regrows=`), `radius` = class, `border` = layer, `bx/by` its size in texels, UV 0..65535 in `tx/ty`, tint in `cx/cy`, its mip levels made on the CPU by `imageMipChain` and filtered trilinearly in the shader, so every GL draws the same pixels (`docs/architecture.md` → "Images: mip levels on the CPU, filtered in the shader") / **3 line segment**: the first endpoint in `cx/cy` (the second is its negation, the quad centred on the segment), the neighbour points `drawLine` was given in `bx/by` (previous) and `dx/dy` (next, else the second endpoint) with which it holds in `radius` / **4 SDF rounded-rect** / 5 icon / **6 bilinear** / **7 checker** / **8 grid**: `drawGrid`'s lines every spacing px from a phase, a whole-px stroke each, majors in `dx/dy`, minors in `cx/cy`, the spacing a float's bits in `tx/ty` and the phases in `bx/by`, unpacked by the vertex shader, a NodeGraph's whole grid in one slot / **9 trapezoid**: `drawTrapezoid`'s vertical sides snapped as `translate()` snaps an edge, so neighbours share a device column edge with no seam, its top and bottom edges at `y*scale` unsnapped, the four heights floats' bits in `cx/cy`, `bx/by`, `dx/dy` and `radius/border` (device px from the quad's top), turned per vertex into `pixelArea()`'s terms, a pixel covered by its exact area between the edges (crossed edges included), a Chart area's segment, `tests/trapezoids.cpp`); `show/hidePrimitive` just toggle `style`. Text uses a separate freetype-gl buffer keyed by text id, drawn by its own program (`m_textProgram`) from a one-channel `GL_R8` coverage atlas per font (depth 1, light vertical-only autohinting, whole-pixel advances, pens and kerning, coverage applied once by the blend; see `docs/architecture.md` → "Grayscale text on the pixel grid"). **LCD subpixel text is opt-in**: `SlotRenderer::setTextAA(TextAA::LcdRGB/LcdBGR)` or `GWENI_TEXT_AA=gray|rgb|bgr` (read at construction; Grayscale by default, byte-identical to the grayscale path) loads coverage-range fonts into a depth-3 `GL_RGB8` atlas (the mode is in the `FontKey`) drawn with dual-source blending (`GL_SRC1_COLOR`). Its glyphs are light-hinted with unhinted fractional advances and kerning, and each pen is rounded to 1/3 device px: the quad on the whole pixel below, the image rasterised at that phase (freetype-gl's `texture_font_t::subpixel_positions` and `texture_font_get_glyph_phase`, a gweni patch; the vertex's `shift` is `phase/3`). The LCD shader branch raises light text's subpixel coverage by `c*(k+1)/(c*k+1)`, `k = setTextContrast()` (or `GWENI_TEXT_CONTRAST=<f>`, default 1) times the text colour's luminance; grayscale and SDF ignore it. A runtime switch replaces those fonts and raises `textLayoutSerial()`, which makes `Canvas::updateCanvas` re-lay the whole tree as a scale change does (`docs/architecture.md` → "LCD subpixel text"). `tools/capture_samples.sh` forces `gray`.

### Hybrid text: coverage below the threshold, SDF at or above it
`SlotRenderer::resolveFont` picks each font's atlas from its effective size `px = textPx(font) = font.size*scale()`: below `m_sdfTextMin` (default 18, env `GWENI_SDF_TEXT_MIN=<px>` read once at construction; `0` = SDF everywhere, a large value = coverage everywhere) it is a hinted grayscale coverage atlas keyed `(face, coverageSize(px), bold)`, `px` rounded half up to a whole device px in every tree and at every canvas scale (an LCD atlas keeps the exact px), laid out by freetype-gl's `text_buffer_add_text`, its glyphs at the measured pens (`measuredPenShifts`), so a continuous zoom passes through whole sizes only; at or above it, one **R8 signed-distance-field atlas per `(face, bold)`** (key size 0), shared by every size. The SDF glyphs come from FreeType's own `FT_RENDER_MODE_SDF` (vcpkg FreeType 2.15 has the `sdf` module), through a gweni patch in `deps/freetype-gl/texture-font.c` (`texture_font_t::sdf_spread`): unhinted at 48 px, spread 6 px, unhinted `linearHoriAdvance`. `SlotRenderer::layoutSdfText` lays an SDF run out for both `measureText` and `renderText` (so `sizeToContents` fits what is drawn): metrics scaled by `px/48`, the baseline on a whole pixel. The text shader's `textMode` 1 is `smoothstep(0.5-w, 0.5+w, d)` with `w` from the field's screen-space gradient, straight alpha, and a `discard` where it draws nothing, as in every text mode (an SDF quad reaches the spread past its ink, and a long run's glyphs can share a depth, so an empty pixel must not write depth over its neighbours). A size change inside the SDF range rewrites only that run's vertex slots, with no atlas upload. `loadFont`/`freeFont` are a counted pair (`FontData::owners`): a font is freed only when every successful load has been matched by a `freeFont`, and even then, in any mode, it is deleted only if no run is laid out in it; otherwise it is marked `FontData::freed` and deleted when its last run leaves it (`setTextRunFont`), or kept if a `loadFont` owns it again first, so one Label changing size or being deleted leaves the face's other sizes, and other Texts in an equal font, drawing. A font loaded only by a use (`ensureFont`) has no owner and goes `SlotRenderer::kIdleFontFlushes` (60) flushes after its last run left it unless a run or a `loadFont` takes it back first, so the sizes a zoom or a canvas scale passes through do not stay and one come back to within a second is not rasterised again (`docs/architecture.md` → "Coverage sizes are whole device px"). **At a canvas scale** `renderText` draws at `px = font.size*scale()` from its snapped device-pixel origin (`TextRun::px` is in the run cache key, so a scale change re-lays a run even inside the shared SDF atlas), while `measureText` measures at `font.size` and returns **canvas units**, identical at every scale (unlike the legacy OpenGL/Software renderers, which return scaled pixels). Where the run is drawn as grayscale coverage, measured as coverage or (an SDF `font.size` drawn below the threshold, at a scale below 1) as SDF, `measuredPenShifts` puts each drawn glyph at its measured pen position times the scale, rounded to a whole pixel, so the run ends where the layout sized it; `freeFont` also frees the measure-only font when no run uses it (`docs/architecture.md` → "Text at a canvas scale").

### Glyph fallback chain, ignorables and terminal cells
A codepoint a run's face has no glyph for is drawn from the first face of that face's **glyph fallback chain** that has one (`SlotRenderer::setGlyphFallback(face, chain)`, `""` the default chain; the skin config's `"fontFallback"`, whose shipped default is `[DejaVuSansMono]`, the mono face's own chain empty), in the same run, atlas and draw: freetype-gl's `texture_font_t::fallback` callback (a gweni patch) makes each chain face, on the primary's first miss and never before, one more `texture_font_t` on the primary's atlas at its size and mode (coverage, LCD or SDF), from the face's file read into memory once and shared (`glyphFallbackBlob`); it lives and dies with the primary's `FontData`. Only when no chain face has it does the face's own missing glyph show. A chain glyph takes its own face's advance, and no pair across two faces is kerned; the line height and baseline are the run's face's. A run whose codepoints are all its face's opens and reads no chain face and lays out, rasterises and draws byte for byte as without a chain (`tests/glyphFallbackText.cpp`). This is not `setFallbackFont`, the built-in OpenSans for a face whose *file* is missing. The default-ignorables (U+200B..200D, U+2060, U+FE00..FE0F, U+FEFF; `ftgl::utf8_is_ignorable`) draw nothing and take no advance or glyph slot in every mode. A run in an `FT_IS_FIXED_WIDTH` face lays every codepoint in whole terminal cells, `gweni::text::cellCount` (`include/gweni/text/cells.h`: 2 for East Asian Wide/Fullwidth by codepoint whichever face draws it, so ⚡ takes 2; 0 for combining marks and the ignorables; 1 otherwise), the cell its advance for `0` and each glyph centred in its cells (`texture_font_cell_place`), with no kerning; the tables are `source/text/cellWidthTable.inc`, generated by `tools/gen_cell_widths.py` from the Unicode version it names (18.0.0). `docs/architecture.md` → "Font fallback".

### Syntax highlighting: tokenizers, the incremental cache, colour spans
`text::Tokenizer` (`include/gweni/text/tokenizer.h`) tokenizes one line from the `TokenState` it starts in (six `uint32_t` words, compared to tell whether an edit changed what the next line starts in; `nested()`/`inner()` keep one language's state after another's first word) into `Token`s (a byte range and a `TokenKind`: plain, keyword, string, number, comment, key, punctuation, heading, emphasis, strong, code, link, template, added, removed, hunk, meta) and returns the next line's state; a tokenizer keeps nothing between calls. The registry (`findLanguage`, `registerLanguage`, `languageNames`) holds the built-ins, one hand-written state machine each in `source/text/highlight/` (`yaml`, `json` with JSONC comments, `diff`, `bash`, `markdown` with fenced code tokenized in the fence's language, its state nested in the fence's, and `markdown+jinja`, `text::makeJinjaOverlay(host)` over Markdown: `{{ }}`, `{% %}` and `{# #}` cut out first, over lines too, the host tokenizing the line with each tag a word of as many letters, a line wholly inside tags leaving the host's state as it was); `languageForFileName` maps `*.yaml`/`*.yml`, `*.json`, `*.md`, `*.md.j2`, `*.diff`/`*.patch` and `*.sh`. `text::HighlightCache` (`include/gweni/text/highlightCache.h`) keeps each line's tokens, start and end state over a `Document` (its own observer, `attach`, or a caller's `linesChanged()`): lines `[0, frontier())` are fresh, a line past it is compared (text unchanged, start state the previous line's end) and tokenized only if that fails, so an edit tokenizes its lines and one that changes the end state tokenizes through the last line on screen (`setVisibleLines`) and no further, the rest done when asked for (`tokens(line)`, as a row is bound); inserted and removed lines shift the entries after them untokenized; `setChangeHandler` gets the lines an edit's pass gave new tokens. The tests are `tests/unit/highlight*.cpp` (hand-written expected tokens per language, seeded random edits through the cache equal to a fresh tokenize, a well-formed and repeatable fuzz over every built-in) and `tests/unit/codeEditorHighlight.cpp`; `tests/colorSpans.cpp` holds the span overload on both backends (`docs/architecture.md` → "Syntax highlighting", "Colour spans in a text run").

### SDF rounded-rect path (the active visual style)
Style 4 is an analytic **signed-distance-field** rounded rectangle drawn in the fragment shader (`drawRoundedRect` on `renderer::Base`): vertical gradient fill + optional border, anti-aliased with a 1 px box filter (`clamp(0.5 - d/aa, 0, 1)`, the border likewise), so a pixel-aligned straight edge covers its outermost pixel fully and nothing outside, rects that abut leave no seam and an N px border is N whole rows; only a corner arc is partly covered. A pixel styles 4, 6 or 7 leave uncovered (outside a corner arc) is discarded and writes no depth, so a slot behind drawn after it still shows there (`tests/uncoveredDepth.cpp`). Its overload with an edge mask (`renderer::RoundedEdge`, packed in `Vertex::radius`'s high byte, so the radius is at most 255 device px; `renderer::Base`'s default drops the mask) makes the corners it names square and keeps the border off the sides it names, and its `reach` widens the quad on those sides by `max(1, snap(reach))` device px, so a tab drawn to its page frame's outer edge covers exactly the frame's border rows at any scale, for a tab joined to its page (`docs/architecture.md` → "OpenGLCore renderer (retained model)", the `Vertex` fields). The quad is exactly the rect: `lx/ly` are in half-pixel units (`±w`/`±h`, halved in the vertex shader), so odd sizes are exact. Style 5 is an **icon glyph** (`drawIcon`, `radius` = kind): a stroked SDF checkmark (0) or directional chevron (1) (checkbox ticks, combo/scrollbar arrows), and the window buttons' cross (2), dash (3), square (4) and restore (5), a separator's rule (6), and a filled triangle (7) and its outline (8), pointing as the chevron does (a NodeGraph's triangle pins). Kinds 2-6 are computed in device px over the square centred in the quad (the rule: the quad's whole length, horizontal for direction 0 and vertical for 1, through the floor of its middle), stroked `max(1, snap(1))` px (in `bx`'s high byte) with style 4's box filter, so the dash, squares and rule are whole fully covered rows and columns, and a rule is that thick wherever it lands on the pixel grid (a 1-unit rect snapped by `translate()` alone is 1 or 2 px depending on its position at 1.25 and 1.5). A style 5 pixel with less than half an 8-bit step of coverage is discarded, so it writes no depth (the textured `Separator` draws its rule one unit past it on both sides, over its neighbours). Style 3 is a **line segment** (`drawLine(id, p0, p1, thickness, z, prev, next)`, `PointF` endpoints in canvas units, the optional neighbours the polyline's points before `p0` and after `p1`): a capsule (round caps) `max(1, snap(thickness))` whole device px thick, each endpoint coordinate placed so the stroke across it starts on a whole px, so a horizontal or vertical segment is whole fully covered rows (columns); a pixel is covered by the exact area of it between the stroke's two edges (`pixelArea()`, a straight edge across the pixel normal to the direction from the segment's nearest point), so a thin slanted line is as bright on every row. A partly covered line pixel writes its depth up to half a layer behind its z (`mix(depth(z-0.5), depth(z), coverage)`, through `gl_FragDepth`, which every other style writes as `gl_FragCoord.z`), so the next segment of a polyline at the same z still draws over an earlier one's anti-aliased cap rim, while a fully covered pixel is blended once; one with less than half an 8-bit step of coverage is discarded, as for style 5. Segments drawn with their neighbours do not leave a joint to depth: the one nearest a pixel's centre draws it (ties to the earlier, every slot computing the same distances from the half-px-rounded centre through one `lineOffset()` loop) at the union of its and its nearer neighbour's coverage, and the others discard it, so a translucent polyline is blended once at every joint pixel on any depth buffer or backend; segments two or more apart keep the depth rule, and a neighbour 16383.5 px or more from the quad's centre is left out (`tests/lines.cpp`; `docs/architecture.md` → "Line segments (style 3)"). `renderer::Base`'s default is a filled rect along the longer axis (`docs/architecture.md` → "Line segments (style 3)"). Style 6 is a **four-corner bilinear fill** (`drawBilinearRect`, for a colour picker's saturation/value box): each vertex carries its own top-edge colour in color0 and bottom-edge colour in color3, both linear in x, so the shader's `mix` along y is exact with no diagonal crease. Style 7 is a **checker composite** (`drawCheckerRect`, for alpha previews): color0 with its alpha over 4 px cells of color1 (light) and color3 (dark), output opaque so the result does not depend on slot/draw order. Styles 4, 6 and 7 share one rounded mask, AA and border (`roundedRect()` in the fragment shader, `writeRoundedQuad()` on the CPU side); `renderer::Base`'s defaults for 6 and 7 approximate them with `drawRoundedRect`. The SDF fields are zero for all other styles, so the fill/texture/text paths are unchanged. Overlay primitives (checkmark, radio dot, arrows) must be drawn at `getZIndex()+1` so the `GL_LESS` depth test doesn't reject them behind their own background. A skin Control that draws at `+1` (or higher) must report it through `skin::Control::depthLayers()` (the z values it uses from `getZIndex()` on; `Base::renumberZRecursive` advances by it, and reads it only when the canvas renumbers, so a Control's count is fixed for its life unless it calls `Canvas::invalidateZOrder()`, or, for a count that follows its control (`skin::Control::depthLayersOf(control)`, a Chart's layer per series), the control calls `Base::zOrderChanged()`), otherwise its first child shares that depth; the textured `ProgressBar` reports 2 for its fill. What a Control draws in front of its own children goes at `getOverlayZIndex()`, the z after its subtree, which it reserves with `skin::Control::overlayLayers()` (read like `depthLayers()`); the textured `TextBox` draws its caret there, its selection at the text's z (`TextBox::getTextZIndex()`), and a text run's glyph i sits at `z+(i+1)/(glyphs+1)`, so a rect at the Text's z is behind every glyph (`docs/architecture.md` → "The TextBox caret and selection"). The textured skin drives it through `tokyonight::Surface` + `paintSurface()` (`include/gweni/skins/textured/tokyoNight.h`) and the `RoundedPrimitive` helper (`texturedPrimitives.h`); each control renderer's `update()` just picks a `Surface` for its state. The default theme is **Tokyo Night** (dark, blue-toned): surface fills are mutable globals in `tokyoNight.h`, text/line colors are set in code by `TexturedSkin::setThemeColors()`, and `renderText` bakes the control's draw color into the glyphs so per-control text colors apply; its overload with `renderer::ColorSpan`s (byte ranges, each a colour; `renderer::Base`'s default draws the run in the first span's colour) bakes each glyph's span colour, and a change of the spans or the colour alone rewrites only the glyph slots whose colour changed and lays nothing out (`SlotRenderer::colorTextRun`; the spans kept beside the run, by text id, so a plain run is what it was; `docs/architecture.md` → "Colour spans in a text run"). **The theme is swappable without recompiling**: an optional `"theme"` object in `resources/DefaultSkin.json` (`surfaces` + `textColors` + `metrics`) is loaded by `TexturedSkin::loadTheme()` and overrides any surface (by name, via `tokyonight::surfaceRegistry()`), text color or size (`skin::Base::Metrics`: `ScrollBarThickness`, a scroll bar's thickness and its square arrows' side, 12 in Tokyo Night and 15 in any other skin, read by the bar when it lays out); omitted entries keep the compiled defaults; `tools::ThemeEditor` edits, saves and loads it live. With `"strict": true` in that object (opt-in; the shipped file does not set it) every surface's `top`/`bottom`/`border` and every text colour in `TexturedSkin::textColorRegistry()` (the 62 names `"textColors"` takes) start as `colors::Missing` before the file is applied, so whatever it does not set, field by field, draws magenta (`radius`/`borderWidth` keep their compiled values), and one stderr line per kind lists the gaps (`theme strict: 177 of 181 surfaces not set: ..., ButtonOn, ...`, the shipped theme made strict); a surface that is transparent at rest (`WindowButton`, `SelectableHover`) turns magenta too unless the theme sets it to `[0,0,0,0]`, and strict gaps fail nothing (`init` stays `true`, a capture exits 0; `docs/architecture.md` → "The theme file and strict mode"). A skin config that cannot be used (missing, a directory, unreadable, not parsing, or not a JSON object) makes `TexturedSkin::init` print one stderr line naming it and return `false` with the skin still usable: every registered surface in `colors::Missing` (magenta, `colors::MissingDark` borders, through `tokyonight::setAllSurfacesMissing()`) and the text colours at their compiled defaults. An atlas texture (`textureFileName`) that does not load is reported and fails `init` too, but the rest of the config, the theme included, still applies. A missing image (`drawMissingImage`) is the same magenta. The legacy 9-slice atlas path (`BorderedPrimitive`) still exists but is no longer used by the converted controls.

When adding or modifying a control, the rule is: mutating anything visual must call the appropriate `addStateChange(...)` (or `addStateChangeRecursive`) so the primitive gets regenerated — otherwise the change won't appear. `redraw()` does this for interaction state (hover, press, focus, disabled): it re-runs `updateColors()` and marks `StateChange_Background` on that control only, then sets the canvas's `needsRedraw()` flag; it no longer walks the ancestors. Issue it from the update phase, since the render phase clears the state change after rendering the control. Conversely, don't redraw unconditionally; that defeats the whole design.

Every control type needs a skin renderer of its own or an intermediate ancestor's (`TextBoxNumeric` draws as a `TextBox`). `Base::setSkin` looks one up by type name, walking up the parent types; if the walk ends at the skin's `Base` entry, it prints `gweni: no skin renderer for <TypeName>` on stderr, once per type and in every build, and records the type in `gweni::controls::typesWithoutSkinRenderer()`. ControlTest exits non-zero if that set is not empty, so `controltest_teardown` (which builds every demo) fails. A type that draws nothing by design (a layout or pure container, a part its parent's renderer paints, a control drawing itself in `render()`) opts out with `GWENI_DRAWS_NOTHING` in its class body, an override of `drawsNothing()` that holds for that type only, so a subclass with no renderer is still reported (`SliderBar` derives from `Dragger`, which opts out). A visual control still waiting for its renderer gets an empty one registered with `GWENI_PENDING_RENDERER` in `texturedControls.h`, citing the issue that tracks the real one, not a `drawsNothing()` override. Renderer names are bare type names, so the `property::` controls `Text`, `CheckBox` and `ComboBox` get the real controls' renderers: those `dynamic_cast` and draw nothing for anything else.

**Current state vs goal:** incremental upload is in place — `SlotRenderer::flush()` records which primitive slots were written (reported, backend-independently, by `renderer::Base::frameStats()` and by id in `writtenPrimitiveIds()`/`writtenTextIds()`, a glyph slot under the text id whose run last held it; `renderer::Base`'s defaults say not counted), uploads only those as coalesced ranges (`glBufferSubData` in `OpenGLCore`), and skips the transfer entirely when nothing changed (the draw still happens every frame). A slot counts as changed only if its bytes differ, because the skin re-emits unchanged controls every frame. Buffers grow geometrically, to 1.5 times the mirror (the clip-box textures by power-of-two rows), and only that frame sends the whole mirror (`FrameStats::bufferRegrows`, `buffer_regrows=`); any other frame sends the dirty slots and the ones the mirror gained. A text run that outgrew its slots gets a quarter more, in multiples of 8 (`allocateTextRun`), so a line typed into grows in place (`docs/architecture.md` → "Incremental GPU upload"). Glyphs outside the ASCII cache are rasterised lazily into the CPU font atlas, and `flush()` uploads the rows they touched (a dirty row band added to the vendored freetype-gl's `texture_atlas_t`) before drawing. `GWENI_UPLOAD_STATS=1` prints per-frame upload calls/bytes (atlas uploads separately, the clip-box textures included) and the primitive slots drawn of the mirror's, in how many ranges; `GWENI_TEXT_DEBUG=<substring>` dumps `measureText`'s glyph metrics and the text mirror slots for matching strings; `GWENI_CLIP_DEBUG=<inset px>` shrinks every clip box by the inset on each side, so the shader clipping shows on screen. Clipping is done in the fragment shaders: every primitive and glyph slot carries the `clipRegion()` it was drawn in (a `Box`, scaled and clamped), read from a 2D `GL_RGBA16UI` texture, `SlotRenderer::kClipColumns` (2048) slots a row (slot `s` at texel `(s % 2048, s / 2048)`), uploaded per dirty run as one `glTexSubImage2D` per row piece, its height a power of two (llvmpipe compiles a shader variant per sampler shape). Both programs take the slot from the vertex shader as a `flat uint`, `slotBase + (gl_VertexID >> 2)`: each chunk is drawn from index 0 of its own slots, 4 vertexes per slot, and the `slotBase` uniform is the chunk's first slot (no `gl_PrimitiveID`, which GLSL ES 3.00 lacks). Text is drawn as one `glMultiDrawElements` (without multi-draw, or with `GWENI_NO_MULTI_DRAW=1`, the same ranges as a loop of `glDrawElements`, counted as one draw) per font atlas and index chunk its runs reach (one per atlas until the glyph slots outgrow a chunk), over the glyphs in use of the runs laid out in that font that are not hidden (each `TextRun` records its `FontData`, which lists its runs; `buildTextDrawList` splits them at the chunks' edges), so the text shader takes the slot from `slotBase + (gl_VertexID >> 2)` instead. That draw list is what keeps a hidden or freed run and a shrunk run's tail off the screen; no index is written for them, so hiding, showing or shrinking a run uploads nothing but its changed vertexes. A Vulkan backend would do the same with device-local buffers + a staging upload. Each control with `shouldClip()` (all but `TabStrip`, `TabButton`, `Text` and `Label`, which clips each child to a rect of its own instead: its bounds, and its Text's widened by `Label::inkMargin()` on both sides while the Text lies wholly inside it, so ink past the measured pens shows; `docs/architecture.md` → "Ink past the pens: the Label's clip margin") narrows the region for its children as the render drain rebuilds their state (`Base::drainRenderQueue`, `addClipRegion`'s rule: its bounds at its absolute origin, intersected with the parent's region; no overlap gives an empty rect), while its own `render()` stays clipped by its parent's; a control may narrow one child's region further (`Base::getChildClipRect`, which hit-testing honours too): a ScrollControl clips its inner panel to its viewport, so scrolled content never draws or takes the mouse in the inset band. A region changes only with an ancestor's bounds, and `onBoundsChanged` marks that subtree when its children's region can have changed (a move; a new size of a control with child clip rects, `hasChildClipRects()`, or of a clipping one whose bounds within its parent's region changed, `Base::childRegionChanged`), so the new boxes reach exactly the controls under it; nothing below a control may draw from that control's size unless its arrange gives it new bounds. Clean, fully clipped controls are never rendered, and dirty ones are re-stamped (with the empty box): nothing is culled on the CPU. Still open: cache-to-texture and free-slot compaction — see `docs/architecture.md` → "Current state vs. goals".

### Controls
- Construct via the canvas: `canvas->newChild<SomeControl>()` or the `newControl<T>(name)` / `T::newInstance(name)` factory pattern. Controls form a parent/child tree (`Base::List`), set up by `setParent`.
- `hidden()` is a control's own flag (what `setHidden`/`hide`/`show` last set on it); `visible()` is whether it is drawn, false when it or any ancestor is hidden (cached, O(1)). Hiding or showing a control never writes its descendants' flags, so the parts a control hid itself (a ComboBox's list, a TabControl's other pages, a collapsed node) stay hidden when a hidden page holding it is shown, and a `setHidden` override runs only for its own control. Ask `hidden()` about a direct child in a walk that stops at hidden controls, `visible()` about whether something is on screen (`docs/architecture.md` → "Hidden and visible").
- `ImagePanel` (`controls/imagePanel.h`) draws one image from a file (`setImage`), encoded bytes (`setImageData`, a PNG or JPEG found from its first bytes) or RGBA pixels (`setImagePixels`), each kept at an optional longest side (`maxSize`, image px; the renderer reduces it through its mip chain, a JPEG decoded at 1/2..1/8, a load over 64 MP or past 2048 px with no max size failing from the header); `clearImage()` frees it, every set frees the one before and the same set again marks nothing. An empty panel hides its slot; only a failed load draws the missing image. `setScaleMode(Stretch|Fit|Fill|None)` places it (`placeImage`; Fill and None crop through the UVs; None is 1 image px a logical unit); `setStretch` is Stretch or None. The loaders are `IResourceLoader::loadTexture(texture, bytes, size, maxSize)` and `loadTexturePixels(...)`, with `loadedTextureCount()` for leak checks (`docs/architecture.md` → "Images from memory"). ImagePanelDemo shows the modes; ImageGridDemo (ControlTest's `--list`, not the shell, whose bad-data cell logs a line) a scrolling `layout::Tile` of embedded images, its preferred height its rows at its width.
- `Separator` (`controls/separator.h`) is a 1-unit rule, horizontal or vertical (`setVertical()`, which also makes it grow along the rule only), as long as its dock or layout makes it, with an optional caption (`setText`, imgui's SeparatorText) `captionInset()` in from the left that the rule runs around; `MenuDivider` derives from it, so menu dividers draw with the same renderer. `Bullet` (`controls/bullet.h`) is a Label with a circle in its text colour in a left column of its font's size plus a gap (imgui's Bullet/BulletText). SeparatorDemo shows both.
- `TextBox::setPlaceholder` shows a hint in the skin's `PlaceholderText` colour while the box is empty and unfocused: a second Text child that is not content (not `getText()`, not in the box's size) and is only ever shown or hidden (`docs/architecture.md` → "The TextBox placeholder").
- A `TextBox` (so `PasswordTextBox`, `TextBoxNumeric` and `NumericUpDown`) has a validation state: `setError(text)`/`clearError()` (`hasError`, `getError`, `onErrorChanged` once per change of the text), `setHelperText`, shown while there is no error, and `setValidator(fn, ValidateOn::Change|FocusLoss)` (FocusLoss by default; Return in a single-line box runs it either way; `validate()` on demand; its result goes through `setError`), all on a message line under the field: an Owner-placed `internal::Text` made on first use, in the box's font one size smaller, never masked, not content (a press on it moves no caret), cut at the box's edge, in the skin's `ErrorText` or `HelperText` colour. Its room (`getMessageRoom()`) is in the box's bottom padding (`getPadding()`/`setPadding()` are the field's) and in its request through `Base::requestedSizeExtra()`, so the frame (drawn at `getFieldHeight()`), the text, the caret and a NumericUpDown's buttons stay above it; it is reserved from the first `setHelperText`, `setValidator`, `setReserveMessageLine(true)` or `setError` and kept, so a field grows once and then a message set or cleared lays out the box alone, writing its frame's slot and the message's glyphs. The textured renderer draws the `TextBoxError`, `TextBoxErrorFocus` and `TextBoxErrorDisabled` surfaces (the theme's red) while `hasError()` (`docs/architecture.md` → "The field validation state"). FieldValidationDemo (the shell's "Field validation") shows each field type.
- A `TextBox` (and `TextBoxMultiline`, `TextBoxNumeric`, `PasswordTextBox`, DragNumber's edit box) has undo and redo: Ctrl+Z, Ctrl+Y and Ctrl+Shift+Z (`undo()`, `redo()`, `getUndoStack()`) give back the text, caret and selection before or after a step, with one `onTextChanged`. Every edit from its keys, its clipboard and `insertText`/`deleteText` is a record on a `text::UndoStack` (`include/gweni/text/undoStack.h`). Typing joins one step until the caret moves, a newline is typed, the kind of edit changes or a second passes on the platform clock; a paste and a cut are steps of their own. A paste (a TextBox's and a CodeEditor's) asks `platform::requestClipboardText` and inserts the text when it comes, looking the control up by id (`Base::getControlById`, null once it is deleted), so a late answer for a deleted box does nothing (`tests/unit/clipboardBackend.cpp`). The app's `setText()` clears the history when it changes the text, and so does one from an `onTextChanged` handler during an edit, which is then not recorded. The stack and `text::Document` (a text as a vector of lines, with invertible edit records and line-change observers, for the coming code editor) are headless (`docs/architecture.md` → "The document and undo model"). `Base::acceleratorKey()` puts an accelerator's Ctrl before its Shift, whichever order it is written in.
- `Selectable` (`controls/selectable.h`) is a row that highlights while hovered and stays highlighted while selected (imgui's Selectable): a click toggles it (`setToggleable(false)`: only selects), Space and Return press it, `onSelect`/`onDeselect` fire on a real change. `SelectableGroup` is a plain object holding at most one selected row (`getSelected()`, `onSelectionChange`). FlowDemo (ControlTest's `--list`, not the shell) is 12 wrapped-text cards with breakpoints at 1024 and 1536.

The wheel has two axes (`IInputEvent::inputMouseWheelH`, non-pure, `false` by default; `Base::onMouseWheeledH`, bubbling as `onMouseWheeled` does; `ScrollControl::onMouseWheeledH` moving its horizontal bar, else bubbling; `GLFW3::processScroll` passing GLFW's x offset, the browser's `deltaX` in a page; `InputCapture::captureMouseWheel(delta, Dim)`), and `Canvas` turns Shift+wheel into the horizontal wheel for every translator. A vertical wheel over a body is the body's whether it scrolled, hit an end or fits (no chaining to the board); over a header, a gap or the board's inset it bubbles to the Board, which scrolls sideways; a horizontal wheel or Shift+wheel anywhere scrolls the board. Adding cards or growing text keeps every offset. Both draw nothing themselves (`GWENI_DRAWS_NOTHING`) (`docs/architecture.md` → "The horizontal wheel", "The board: columns that scroll on their own"; `docs/layout.md` → "Board"). BoardDemo (the shell's, ControlTest's `--list`) is five columns of wrapped cards, an overflowing Backlog and a fitting Ready.
- Layout helpers (`align.h`, `controls/layout/`) and docking (`DockPosition` in `uiTypes.h`) handle positioning.

### Skins
A skin is constructed around a renderer and `init()`'d from a resource: the textured skin loads `DefaultSkin.json` (atlas description) + a TTF font. The faces are `resources/*.ttf`, each with its `*-LICENSE.txt` (OpenSans, LiberationSans-Regular, and DejaVuSansMono, the monospace face, Bitstream Vera's license with DejaVu's public-domain changes). The config's `"monoFont"` is `skin::Base::getDefaultMonoFont()` (DejaVu Sans Mono 11, not loaded until a control uses it), for code and logs without naming a file, and its `"fontFallback"` (`{"default": ["DejaVuSansMono"], "<face>": [...]}`) is the renderer's glyph fallback chain (`SlotRenderer::setGlyphFallback`, below). `texturedControls.cpp` / `texturedPrimitives.cpp` map each control type to its primitive layout in the atlas.

### Events
`event::Handler` is a base of `controls::Base`. Hooks carry an optional `event::Packet` (a `std::variant<Base*, String, int, float, size_t>`) delivered via `event::Info`. Use `Packet::isControl()/isString()/...` + `get<T>()` to unpack.

## Conventions
- C++17, `lowerCamelCase` for methods/functions, `PascalCase` for types, member fields prefixed `m_`.
- Public symbols crossing the library boundary are tagged `GWENI_EXPORT` (`export.h`).
- `gweni::String` / `gweni::Point` / `gweni::Rect` / `gweni::Color` / `BoundingBox` (aliased to `Margin`/`Padding`) come from `platforms/platformTypes.h` and `uiTypes.h` — use these rather than raw types.
- Filesystem backend is selected at configure time via `GWENI_USE_FILESYSTEM` (std / experimental / boost) based on compiler; code must go through that macro, not include `<filesystem>` directly.
- Verbose per-control debug output (`logUpdates` → `printf`, plus `DEBUG_ID` and `DEBUG_LAYOUT` in `base.h`) is off by default and enabled by configuring with `-DGWENI_DEBUG_LOGGING=ON`; expect verbose stdout when running such a build. `DEBUG_ID` also appends each control's id to label text, so that build looks different too.
